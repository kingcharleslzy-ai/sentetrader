# AI 自主模拟交易与语音会话 v1

## 1. 目标

AI Trader 在 `liveTrading=disabled`、仅连接 TqKq 模拟账户的前提下，允许 AI 直接提交模拟限价委托、查询或撤销活动委托、减少已有持仓，以及设置确定性的止损触发器。模拟盘不逐张要求本人点击授权，Runtime 按需自动建立内部执行租约。

同一能力可由文字或中文语音驱动。语音只是输入/输出通道，所有交易动作仍经过同一个 Runtime、风险规则、幂等键、TqKq 单笔网关和审计链；语音识别和模型循环都不能直接访问 `TqApi`、快期凭据或 Sidecar 令牌。桌面端默认登录云端账号使用服务端模型池（DeepSeek V4.1 Flash、GLM 5.3 Flash，Kimi K3.1 Pro 按会员档位可选），本机环境可用自带 DeepSeek Key 或 ChatGPT；更换模型供应商不会扩大交易权限。

## 2. 模拟执行语义

平台默认不设单笔手数、累计委托数或有效分钟数上限。用户需要时可在设置里启用并调整：

- 单笔最大手数和本会话最多委托数；
- 当前已经生效的确定性风险规则继续作为不可绕过的上限。

只有本机已认证用户可以修改限制或终止执行。AI 不能关闭用户配置的风控，也不能绕过行情、账户、持仓或网关校验。行情/账户/网关不可用、明确停止、急停或超出自定义限制时，所有新动作失败关闭。

“AI 自主执行”只用于 AI 自己发起的操作（策略自动下单、价差执行）：用户消息引起的对话回合里 AI 一律不直接成交，只出卡等确认（所有者 2026-10-16）。设置 → 交易 → “AI 自主执行”（`trade.aiAutonomy`）关闭后，AI 的下单工具、替用户挂止损和执行租约都被 Runtime 拒绝；监控中的策略按各自的执行方式处理信号：只提醒、出卡确认照常，执行方式为“自动下单”的实例在关闭期间改按“出卡确认”处理——信号来了往它的对话里出一张确认卡，用户在卡上确认后才走普通的确认 → 下单（2026-09-25 起，取代原来的“只监控不下单”）。这时把实例的执行方式设为自动下单会被拒绝（409 `ai_autonomy_disabled`）。关闭开关停掉的租约记 `stop_reason = ai_autonomy_off`，不算用户的“停止”：`controls.stopStatus` 不报 STOPPED，用户自己驱动的动作（确认卡、挂自己的止损）照常，开关重新打开后 AI 的下一个动作会建新租约。用户确认的策略开仓卡带的策略保护属于用户自己：开关关闭时照样布防，价格触及照样触发平仓（已布防的保护止损本来只受急停拦截，见 `_stop_authorization` / `_require_exit_allowed`）；只有用户的停止 / 急停（以及只停新开仓对开仓）拒绝确认这张卡，卡上写明原因且不发单。出卡、只提醒和实例自动暂停的消息在语音通话在线时各播报一句。

普通停止和急停只作用于当前交易账户：owner/operator 的停止覆盖该账户所有用户的执行，立即暂停该账户上的策略监控，其他账户的策略不受影响（所有者 2026-10-04）。停止状态不会因为后续行情问答或普通操作建议自动解除；只有该账户的执行负责人再次明确说“恢复/继续 AI 模拟执行”时，Agent 才能调用恢复工具；operator 不能替执行负责人解除围栏或恢复授权。恢复动作本身不下单、不重启已暂停策略，也不会恢复急停时已经取消的委托或止损。

内部租约绑定当前 Runtime 会话；应用或 Runtime 重启后按绑定账户与保存的限制自动建立新租约，不弹确认。用户给 AI 的限时租约到期后（`EXPIRED` 且已过 `expiresAt`），只拒绝 AI 自己发起的动作（`ai_execution_expired`）；用户自己挂止损、确认带保护的下单卡按冷账户处理、照常进行，不再被过期租约挡住（#1206，2026-10-30）。已经创建的确定性保护性止损仍按原唯一订单身份恢复跟踪，未知结果只回读、不重提。

`UNKNOWN` 始终只查询原 `clientOrderId`，不会重新下单。保护性止损只减少已有持仓；触发后只创建一次平仓意图，不做追价撤单重报。

## 3. 执行链

```text
AI 发起模拟动作
  -> Runtime 自动建立或刷新内部执行租约
  -> AI 读取行情/账户/持仓
  -> AI 调用受控模拟交易工具
  -> Runtime 校验用户设置、行情、持仓、Tick、涨跌停与风险规则
  -> 创建可审计交易记录
  -> 复用 SimulationOrderService 生成唯一 clientOrderId
  -> Sidecar 最多调用一次 insert_order
  -> 回读 TqKq 委托/成交/持仓事实
```

撤单只能针对当前用户已经存在、仍可撤且属于允许合约的委托。平仓必须由 Runtime 根据真实持仓决定 `BUY/SELL` 以及 `CLOSE/CLOSETODAY`，AI 不能自行拼接平仓字段。

## 4. 止损

止损是 Runtime 的持久化确定性触发器，不是让模型持续盯盘：

1. 创建时读取当前持仓、方向、可平数量和正常行情；
2. 多仓止损只在最新价小于等于触发价时触发，空仓止损相反；
3. `ARMED -> TRIGGERING` 使用 SQLite 条件更新保证只触发一次；
4. 触发后复用同一平仓校验与单次委托链；
5. 调用网关前先保存唯一平仓 `clientOrderId`；进程中断后不会重发未知委托，只恢复查询与状态回读；
6. 急停阻止新开仓并撤销未触发止损，但不会伪造已经发出的订单结果。
7. 直接保护跟住持仓（2026-10-04）：用户自己挂的（下单顺带、持仓补挂、AI 挂的）保护在每轮扫描前向当前持仓收敛——持仓全平自动撤销并回对话说一声（`last_error = position_closed`）、减仓自动缩手数、隔夜的今仓保护在账户交易日换日后按昨仓平（挂上时记 `account_trading_day`，与账户摘要 `tradingDay` 比较；本站模拟盘结算完成才换日，旧行按创建时间的日历日）；触发后部分成交的平仓单结束（`last_remote_status = FINISHED`）时清掉旧平仓单身份回到 ARMED，剩余量继续收敛；触发平仓委托全部成交时该保护行置 `EXECUTED` 并同时把剩余量清零（2026-10-09 起，此前 EXECUTED 行不再进任何回写路径、剩余量会停在触发前的值）。策略保护（带 `strategy_metadata`）不受影响，仍由成交同步负责；持仓/账户活动快照不新鲜时整轮跳过，绝不在不确定时撤保护。
   锚定原仓（2026-10-06，#528 P1-1）：直接保护挂上时记 `anchor_volume`（该合约、方向、桶当时持有手数）、`closed_since`（此后已平手数）与成交水位 `fill_watermark_json`（`{day, ids}`：最新交易日与当日已处理的 `clientOrderId:tradeId`）。每轮把水位之后同合约、反向的平仓成交（today 桶只计 CLOSETODAY，昨仓桶计 CLOSE/CLOSEYESTERDAY，all 桶计全部平仓）累加进 `closed_since`，含它自己的平仓成交（按成交 id 只计一次）；平仓先算原仓（所有者决定）。有效量＝min(剩余量, anchor−closed_since, 当前该桶持有)；anchor−closed_since≤0 即原仓平完 → CANCELLED（`last_error = anchor_position_closed`），即使同方向又有仓也撤，此时对话发提醒卡（原止损/止盈/手数、现持仓，按钮“问 AI · 重新挂”与“打开持仓”，不自动挂）。开仓成交从不增加保护量。水位跨交易日累计，新交易日只含当日成交也正确；比水位更早交易日的未列成交视为已处理。某合约成交形状不可信（缺交易日、手数/方向/开平读不懂）时该行本轮不改。锚点列为空的旧行在第一次收敛时以当时该桶持有量与现有成交为起点，本轮不据此撤或缩。触发的通知只落在人的会话（native/codex）：行会话被触发改写成 deterministic-stop 内部会话后，回落到该账户最近的对话。
8. 触发通知只说事实（2026-10-04）：平仓单真的提交出去（过了网关派发）才说“已发出平仓单”；提交被挡在网关之前（NOT_DISPATCHED）行回 ARMED、原因 `order_not_dispatched`，下一轮重试同一笔 `clientOrderId`，不误报。
   重派前重新定价（2026-10-12，#750）：只对确定未派发（`PREPARED`：从未发出，或引擎/网关确定拒收、命令没进账本，如 409 `paper_settlement_pending`、`NOT_DISPATCHED`）的保护平仓，在 TRIGGERING 认领与执行许可之后、派发之前，按行上的 `price_intent` 用当前新鲜行情重算限价（`SimulationOrderService.reprice_protective_close`），并重验合约身份、价格网格/涨跌停、当前持仓与今昨桶可平量。只改价时沿用原 `clientOrderId`、原 `commandId`：两种网关对确定未派发的提交都不留命令记录（本站模拟引擎在结算等待时先拒收再写命令行；快期侧车在订单未初始化时入队前就返回 NOT_DISPATCHED），原身份仍可用；万一判断有误、原单其实已被接收，网关按原身份去重回读到旧价，Runtime 记“身份异常”而不是多发一笔平仓。改写委托请求与 `protective-reprice` 审计（前后价格、意图与依据行情）在同一事务，提案是已记录的授权、不改。今昨桶或手数已变（直接保护收敛缩量、隔夜滚桶）时原请求身份不成立：同一事务放弃旧单（`ABANDONED`，审计 `protective-close-replan`）并清掉行上的旧单身份，按新身份重建（中断时行按 528-C 回 ARMED）。已受理、`CALL_STARTED`、`UNKNOWN` 不改价不再发，只按原 ID 回读；用户自己确认的限价单、AI 普通下单不走这条（入口只认 `automationSource = deterministic_stop`）。策略保护在价格变化时不重新规划，同样经 `_fire_protective_close` 这一个入口重定价。等结算价拒收时保护行 `last_error = paper_settlement_pending`（持仓面板“已触发，正在等交易所公布结算价”），重试按保护扫描的在途重试节奏（距上次拒收满 2 秒）而不是每条行情；通知只在真正发出后一次，写实际委托价。
9. 合并卡（2026-10-06）：平仓卡可带 `remainingProtection`（剩余仓位的止损/止盈：给价=改到这个价，null=撤掉，不传=不动），平完全部持仓时 422。确认时在同一事务写 `card_protection_steps`（状态 awaiting_close）；订单看护循环每 2 秒读平仓委托：仍在场上或结果未知就等（未知 30 分钟后 skipped），结束且一手没成交 → skipped，有成交 → 等账户成交回报对上实际成交量后，按当时实际持有的每个桶把该持仓（合约×方向）用户自己挂的直接保护和开仓卡保护撤掉（`CANCELLED`，`last_error = replaced_by_card`，不发“持仓已平”通知；同一持仓的策略保护不动，卡上写“策略「X」的保护不受影响”）并为实际剩余手数挂新的直接保护（同一套价位校验与可平量核对，#528 锚点在平仓之后取）。先全部核对（持仓仍在、没有正在触发的保护、新价位在新鲜现价的正确一侧、可平），任一不过 → failed，什么都不改、原止损保留；撤旧、挂新与第二步状态的最终写入在同一事务，重复确认、重启或两轮清扫都只做一次。按用户本人的操作执行（账户写权限），不看 AI 自主执行开关；策略保护不动。
10. 保本提醒（2026-10-06）：账户提醒循环（30 秒）对挂了用户自己止损且止损劣于开仓均价的持仓判断，浮盈距离 ≥ `notify.breakEvenRule.multiple`×R（R=|均价−止损|，默认 1）或浮动盈亏 ≥ `amount` 元（外盘美元子账户 ≥ `amountUsd` 美元；未设 `amountUsd` 时外盘按倍数，不换汇率）时问一次（`breakeven_notices`，每用户×账户×交易日×合约×方向一行，与消息同事务落库）；快照或行情不新鲜不判。“移到成本”（卡片或口头“移”）只把仍劣于成本的止损条件更新到成本价（止盈不动），先核新鲜现价与最小变动价位，持仓均价与成交取自同一次账户读取（加仓后均价变了，旧卡作废、不移到旧成本）；不下任何委托。

## 5. 语音

实时语音（1.5.1 起，1.6.0 重构为前台/后台）：客户端只搬运音频——麦克风 PCM16/16 kHz 经 Runtime WebSocket `/api/voice/realtime` 到豆包实时语音模型，豆包的语音回到客户端播放；语音密钥只在 Runtime 进程里读取，客户端没有开关。豆包只做前台（听、说、打断、寒暄、澄清、替用户口头“确认/算了”），所有业务请求由 Runtime 在 ASR 定稿时自己发起 `delegate`（1.6.6 起豆包没有 delegate 工具，只有 confirm / cancel / read_screen）原话交给同一聊天会话里的交易 AI（回合 `origin: voice`，绑定客户端 `hello` 报来的窗口与会话），语音权限即 AI 权限；AI 的正文照常进入对话（语音轮次带喇叭标），Runtime 订阅该回合的文本流，把第一段按句切开逐句 `speech_text_buffer.commit` 交豆包念（上一句音频送达后再念下一句；第一句过长时在逗号处先开口；表格/代码块/后续段落不念，末尾念“细节在对话里”），`spoken` 字段即第一段原文，不再二次概括。判停与打断（2026-09-21 起）：判停由豆包动态判停决定，Runtime 看门狗只在 transcript 停更超过账号偏好 `voice.endpointStallSeconds`（2–5 s，默认 3 s）时强制判停兜底。提前判停（2026-09-28）：实测豆包的 partial 在说完约 0.3 s 就带上二遍识别的句号（“确认。”），`completed` 却要再等约 1.3 s，Runtime 念过一句（`speech_text_buffer.commit`）之后常要 2.5–4 s；强制 commit、静音一下都不能让它提前（`input_audio_buffer.clear` 会被拒并断线）。因此由 Runtime 自己答的句子（delegate / 确认 / 取消 / 停 / 挂断 / 追单 / 撤单 / 保本提醒的移与不用，`EARLY_ROUTES`）在出现带句末标点的 partial、且去掉标点后的文字 0.6 s（env `AI_TRADER_VOICE_EARLY_FINAL_SECONDS`，0 关闭）没变时直接按它路由（时间线 `asrEarlyFinal`），这一轮不等豆包的填充语与回复；豆包随后的 `completed` 若是同样的话（或二遍改写）就丢弃（`asrFinalLate`），它对这句的回复被取消（`lateReplyMuted`，工具调用静默作答 `lateToolDropped`；Runtime 自己的播报 `tts_type=chat_tts_text` 不受影响），若多出新字则只把新增部分当作续句路由——不论中间隔了多久（2026-10-08：豆包常把答过的句子留在没关的一段里，下一句的 partial 与 completed 以它开头；原先 10 s ### 5.1 打字与语音共用确定性路由（2026-09-20）

打字回合在进入模型前先过 `rt/turn_router.py` 的确定性分类，语音 delegate 的回合同样受益（语音 fast 通道语义不变）：

- 界面意图表命中的口语（换主题、收面板、切周期、开设置，含"边上的/旁边的"收侧栏）不经过模型，直接走与语音 fast 意图同一条 `run_window_intent` 命令路径，出一行确认；窗口不在线或命令被拒时照旧回落模型回合。
- 下单话（2026-10-16 意图重构第 3 步）先由意图解析器 `order_intent_parse.parse` 读：读得有把握的下单（"搞一手螺纹多的""平掉沪金两手""全部平掉""把螺纹调到三手多单"，以及按分句拆开的一句多单"开多一手螺纹，然后开空两手沪金"）不经过模型，路由 `order_intent` 由规划器直接出卡（多张卡各自发布、各自可点）或出追问卡（快捷选项是补全后的整句），回复一句卡上的数；问句、建议、否定、转述、整句收回、条件单不出卡，路由带 `no_card`，用户消息引起的回合（打字、语音委派、chat:send，所有者 2026-10-16）一律不给也不执行直接成交（`turn_router.DIRECT_FILL_TOOLS` / `fills_directly`：`execute_simulation_trade` 与代确认卡片的路由，app_call 与激活技能同样），只能 `propose_order` 出卡或追问；会自动下单的策略启动（`auto_strategy_start`）只在用户这句话要启动它时执行（这句话是启动命令——启动、上线、恢复、开始监控、改成自动下单——且点到这张策略的名字或“策略/监控”而没点别的策略名，或确认 AI 上一句（回答的最后一句）明确问要不要启动这张策略并点了它的名字（问句本身须点这张策略的名字；只介绍、评价策略或用“它”指代、不点名时说“好”不算，2026-10-20）；问句、介绍、评价、否定不算；直调工具、app_call 的 `tool:start_strategy_monitoring` 与 HTTP 启动路由同一判定），否则 `strategy_start_not_asked`；不出卡的回合则那一轮不给也不执行任何下单写工具（`turn_router.ORDER_WRITE_TOOLS`：出卡、自主下单、撤单、挂撤保护、恢复自主执行、启动策略监控、跑流程，经 app_call 也一样；激活技能也挂不上；模型硬调 `tool_not_offered`；停止自主执行不在其中——“别再下单了”要的正是它），条件单提示可建价格提醒（到价的挂上价格提醒技能）；解析器拿不准但明显是下单的（拆不开的一句多单、改口、两个价格或手数、调到几手、下单句带随单止损止盈…，`ORDER_GAPS`）走 `order` 路由：只带 `{propose_order, search_instruments, get_positions}`，temperature 0、minimal 推理、最多三个工具回合，`card_required`：`propose_order` 回卡、拒绝或追问前每轮 tool_choice=required，只回文字重试一次仍不调就出“没能生成方案卡”（#952 第四轮恢复）；其余拿不准的照常进后续路由，最后是带 `propose_order` 的 general。旧的四条关键词路由、四段下单提示词、`ask_order_details` 与强制出卡轮已删除；界面兜底的交易词排除改为“解析器读出交易意图（含问句以外的语气）就不是界面话”；全平/全撤的说法带了解析器读不了的话（“关掉所有持仓两个合约”“在持仓面板里把所有仓位都关掉”“关闭所有委托中的螺纹单”“关掉所有持仓吗”）也由解析器的 `book_words` 认作交易话，只有动作后面同一分句里跟着界面部件（“关掉所有持仓这个面板”“持仓都关上面板”）才是界面话（第 4 步删掉 `voice_intents` 里的 `close_all_spoken` 与 `_UI_EXCLUDE` 的撤单/限定平仓词）。

### 5.3 平仓卡自动判定今昨、工具拒绝直接转述（2026-09-20 第二轮）

### 5.4 按住说话（2026-09-25）

对话面板输入行发送键旁的麦克风，或按住快捷键（默认右 Alt / 右 Option，设置 → 快捷键 的“按住说话”，本机保存；软件窗口在前台时整个交易台都有效，对话面板没开会随按下自动打开并同时开始录音（按下那一刻的话不丢；策略引导卡在提问时快捷键例外，话作为引导回答发到卡片、不打开对话面板，`setPttTarget`；对话面板输入行自己的麦克风始终发到对话，2026-10-08）；通话中、未连接、语音不可用或模型未就绪时按键不录音，只在对话面板输入行说明原因）。它把话转成文字，文字就是一次普通的用户消息：走 `useWorkspaceChat` 的同一发送入口、同一 `turn_router` 路由与权限，不经过语音前台（没有快问、界面意图、口头确认）。语音回复（2026-09-28）：直接发送的这条消息带 `origin: "ptt"`，Runtime 按语音回合解码（`origin` 仍记为 voice，回答带 `spoken` 口语摘要，对话里带喇叭标），但模型说明换成按住说话版 `PTT_TURN_INSTRUCTION`（方案卡在卡片上确认、没有口头确认），也不带只属于通话的账号设置（免口头确认、通话中不画图）；客户端 `voiceReply` 在发送时就打开 WebSocket `/api/voice/speak`（`voice_speak.py`，豆包会话 1–2 s 建立藏在 AI 回答期间），这条消息之后第一条带 `spoken` 的语音回答到达即发 `{"type":"speak","text":…}`，Runtime 用通话同一音色、语速经 `speech_text_buffer.commit` 念出并按通话格式回传音频（`audio` / `audio_end`）；再次按住、开始通话或离开页面即停止。播放用按住说话在按下手势里创建并 resume 的同一个 AudioContext（`pushToTalkStore.playbackContext()`）：`expect()` 在定稿回来后才调用，已不在手势里，手机上那时新建的 context 停在 suspended、音频到了也不出声（10-05）。鉴权、技能、每日语音分钟与按住说话相同（按念出的秒数计），本账号通话中 4432 拒绝。

- 客户端：采音复用通话的 `MicCapture`（`apps/client/src/micCapture.ts`，16 kHz 单声道、20 ms PCM16 帧），状态 空闲 → 按住中（音量条、计时、实时 partial）→ 识别中 → 已发送或回填。按下不足 0.3 s 不算一句（发 `cancel`、不发送，输入行提示“说话太短，按住说完再松开”，手机同一提示）；按下即进入录音态：麦克风按钮外圈呼吸、音量条从可见的底线随音量起伏，松开后“识别中”音量条依次起伏，减少动态效果时两者都静止；按住时 Esc 取消；松开后再送约 0.2 s 音频再发 `end`；final 为空时输入行提示“没听清，再说一次”、不发送。松开后的行为由账号偏好 `voice.pttSendOnRelease`（默认 true）决定：true 直接发送（AI 还在回答时改为回填），false 回填输入框。通话进行中按钮与快捷键禁用。
- Runtime：WebSocket `/api/voice/transcribe`（`voice_transcribe.py`）。鉴权、origin、`voice-call` 技能、每日语音分钟与 token 日限额和通话相同，时长计入 `add_voice_seconds`（至少 1 秒）；不占每账号一路通话名额，但本账号有通话时以 4432 `call_active` 拒绝；回放命名空间转发的连接照常接受（转写与账户无关）。上游豆包 `session.create` 用只转写的指令、`tools: []`，`asr.extra` 与通话同一个 `asr_settings()`（热词 + 替换词 + 二遍识别）；`session.created` 之前的帧先缓存、之后按序补发。客户端 `{"type":"end"}` 后发 `input_audio_buffer.commit`，并每 100 ms 补一帧底噪直到 `completed`（豆包 3.0 判停后必须继续上行，否则收不到定稿），最长 6 s；按住期间已由豆包自行判停出的定稿会拼在前面，若松开时已无新语音则 1 s 内直接返回（“正在说”只以 delta 为准：豆包开始回复时也会发一个没有字的 `transcription.started`，2026-10-08 线上它让松开后整整等了 6 s 超时）；整个按住期间一次都没检测到说话（没有 `transcription.started` / delta）时，从松开（或 `session.created`，取晚者，保证会话建立前缓存的短句仍能转写）起最多再等 1.5 s，仍无说话即返回 `{"type":"final","text":"","reason":"no_speech"}`，不再等满 6 s（09-25 实测静音按住 1 s 要 6.4 s）。回给客户端 `partial` / `final`（经 `clean_transcript`），超时为 `{"type":"final","text":"","reason":"timeout"}`；客户端对空 final（timeout / no_speech 等）一律提示“没听清，再说一次”；`cancel` 立即关闭、不出结果。豆包对每句判停都会开始回答：转写会话在每个回复的第一个事件（`response.created` 或最早的 `response.*` / 输出音频事件）向上游发一次 `response.cancel`（3.0 官方事件），不生成语音、不计费，其余回复事件忽略；拿到定稿即关闭上游。
- 可观察性：没有界面命令（与快捷键同属用户的物理输入）；快照 `context.voice.ptt`（idle/recording/transcribing）与 `context.voice.pttShortcut`。WebSocket 与 `/api/voice/realtime` 一样不进能力目录与 OpenAPI 基线。

### 5.5 前台直接查询（2026-10-13，开关 `AI_TRADER_VOICE_FRONT_QUERY`）

所有者 2026-10-13 定的方向：让实时语音模型直接调业务工具，交易 AI 只留给重活；本节是第 1 步“查询链路”。开关在 Runtime 环境变量：空 = 关（通话与之前逐项一致：前台说明 `INSTRUCTIONS`、工具 confirm / cancel / read_screen / get_quote / get_positions / get_account、`quick` 路由都不变）；`all` = 全部用户；逗号分隔的 user_id = 只对这些用户。开关在通话开始时读一次；回放绑定的通话不开（新闻、走势会把今天的信息带进历史回放）。

- 前台工具：只读的三个快查合并为一个 `query`（`what` = quote / positions / account / orders / news / brief / analysis，`query` = 品种名，空 = 窗口上的合约），加上 confirm / cancel / read_screen（`FRONT_TOOLS`）。取数全部走页面与 CLI 同一套已认证正式接口：`GET /api/market/{symbol}`、`/api/positions`、`/api/account/summary`、`/api/account/activity`（活动委托：ALIVE 且有未成交量）、`/api/research/flash?product=交易所.品种`（今日新闻要点一句 + 最多 4 条快讯标题，注明第三方未核实）、`/api/app/briefs`（简讯）、`/api/markets/{symbol}/workbench?duration=86400` 再用交易 AI 的同一个确定性摘要 `_market_analysis`（近 60 根日线的趋势、涨跌、5/20 日均价、ATR 波动读法）。返回紧凑中文、≤6 项，价格带单位（`PRICE_UNITS`，螺纹 元/吨、沪金 元/克…），涨跌说“涨/跌 x%”；行情不是最新时照样给价格并在“说明”里讲原因与开盘时间（`session_note`：午休、小节休息、已收盘晚上九点开夜盘、下个交易日上午九点 / 中金所九点半；节假日不判断），不念“行情不是最新状态”。
- 前台说明 `FRONT_INSTRUCTIONS`：豆包自己答查询（先调 query、只念返回）、止损保证金这类概念的大白话解释、寒暄、听不清或半句话的反问、同音误听按上下文纠正；第一句给结论、一般不超过 150 字、不编数字；下单 / 平仓 / 撤单 / 策略 / 设置 / 界面 / “能不能买”这类判断仍一声不吭交给 Runtime（另开了 §5.6 的账号，说全了的下单类由前台直接出卡）。
- 审查补正（2026-10-13，随 #851）：“什么是保证金 / 什么是持仓”按概念解释，不读账户；问 MACD、KD、RSI、布林这类指标的句子交给交易 AI（前台的日线摘要不含这些读数）；说出别名或前缀（黄金 → 沪金）的查询之后，“它多少钱”指这个品种；快讯走 web-research 技能门（基础档、游客、全局停用时念统一的不可用说明，与内置 AI、MCP、CLI 一致）；（周五夜盘照常，审查曾提出周五无夜盘，核实后保持“晚上九点开夜盘”）；纤维板单位 元/立方米；合约目录接口 ok 但没有条目时也改读共享行情目录。
- 路由（`voice_front.classify_front`，纯函数，`tests/test_voice_front.py` 钉表）：Runtime 原路由为 chat / quick / delegate 的句子再判一次——带交易动作、策略、设置、界面词、判断/比较/复合词的仍 delegate，固定意图表命中的界面命令仍走零 LLM 快路径；其余的查询（价格、持仓、资金、委托、新闻、简讯、走势；“它/那个”指通话里刚说过的品种，“那沪金呢”沿用上一句的查询类别）、概念解释、寒暄、半句话（去掉“我想/问一下/帮我/看看/那个…”后什么都不剩）路由为 `front`，时间线 `routed by=front`（带 `front` 类别与 `what`）。
- 谁来念：概念解释、寒暄、半句话由豆包本轮自己回答（它在概念句上调 query 时只拿到“直接解释、不念数字”的提示——本机实测它查了行情就去解释价格）。说出了查询类别的句子：读数在定稿那一刻就开始（预取）；豆包调 query 时用这份结果作答（类别与品种以 Runtime 听到的为准，时间线 `frontToolRemapped`），并在同一轮里用 Runtime 的一句（`spoken_line`）经 `speech_text_buffer.replacement` 替换豆包的措辞——2026-10-13 对线上豆包实测，它自己组织语言要在工具结果回去后再等约 1.1–1.4 s 才出字（说完到开口 2.6–4.4 s），取消它再由 Runtime 另念还要多约 1 s（取消到 `response.done` 约 1 s），同轮替换在定稿后约 1.3 s 出声；解释与寒暄 1.2–1.8 s。豆包没调工具就先开口（凭记忆说数）时，它的回复在出声前取消，Runtime 收到 `response.canceled` 就念（不等随后约 0.5 s 才到的 `response.done`，时间线 `frontQueryFallback`）。提前判停与 `EARLY_ROUTES` 同一机制，但二遍识别的 partial 常在带标点与不带标点两版之间来回，实际很少触发。
- 兜底不转交易 AI：说完没出定稿（`asrStallFinal`）时，查询由 Runtime 念结果，半句话说“你想问什么？”，寒暄“在的，你说”（只有“嗯/好”就不说），概念句请对方再说一遍——实测豆包 3.0 没有“按文字回答”的事件（`response.create` 被拒为 unknown event，单发 `conversation.item.create` 文字不会触发回答），所以没定稿的句子它答不了。豆包一言不发结束的前台轮次：查询与半句话由 Runtime 答，概念句交交易 AI（它的说明让它对判断保持沉默，路由可能判错），寒暄不补。
- 记录：前台答完的每一轮（用户转写 + 念出的回答，`origin: voice`）作为普通 user / assistant `message.completed` 写进通话所在的聊天会话（`record_quick_turn`），交易 AI 已加载的该会话内存历史同步追加这一对（`append_voice_turn`；该会话正有回合在跑时只让它下次从事件重建，不打乱回合的历史标记），挂断后打字追问能接上；每日记忆提炼读的是全部 `role=user` 的 `message.completed`（`store.user_texts_between`），这些语音原话同样在内。Runtime 念的结果也补进豆包上下文。

### 5.6 下单类直接出卡（2026-10-13 第 2 步，开关 `AI_TRADER_VOICE_FRONT_ACTION`）

开关写法同 §5.5（空 = 关、`all`、逗号分隔 user_id），只在前台直接查询也开着的通话里生效；账号开了“语音下单免口头确认”时下单类不走本节（卡一出就会被确认），仍交交易 AI 按原设置处理，撤单照本节；关时前台说明、工具表、路由与 §5.5 逐项一致（`tests/test_voice_front_action.py` 钉住）。安全语义不变：语音只出待确认卡，确认仍是用户口头“确认”或点卡（`confirm` 工具、确认窗口、“语音下单免口头确认”设置都与交易 AI 出的卡同一套）；唯一不出卡的是撤单，见下。

- 品种目录（#754）：通话开始读目录拿不到品种名（部署后头几分钟 products=0）时，每句路由前再读一次目录，空着时最多每 30 s 一次（`CATALOG_RETRY_SECONDS`），读到后整通电话照常认品种。
- 前台工具：在 `FRONT_TOOLS` 后常驻一个 `action`（`kind` = open / close / close_all / target / cancel，品种、方向、手数、价格），说明 `FRONT_ACTION_INSTRUCTIONS` 只把“下单一声不吭”那句换成“明确要下单、平仓、全平、调到几手、撤挂单就调 action，调之前不说话、只念返回”。**常驻而不是按需挂载**：2026-10-13 对线上豆包实测（本机直连、合成语音 17 句，证据 ~/ai-trader-release-artifacts/voice-action-20261013/static1.log、dynamic1.log），听到交易词时用 `session.update` 整表换工具会把正在识别的句子截断（“空两手白银，挂对手价”只剩“挂对手价”、“开三手，不对，两手沪金多单”只剩“三手不对”），换表后 5 次 action 调用有 3 次带着别的工具的参数（`{"query":"白银","what":"quote"}`、`{"amount":1,"variety":"螺纹"}`）；常驻时 7 次调用参数结构全对、识别完整，挂断前问“我刚才让你干什么”两种方式都答得出前文。
- 谁判定：**以 Runtime 从原话听出的为准，豆包的参数只记日志**。同一实测里豆包把“空两手白银”填成 long、“820 挂一手沪金多单”填成 3082 的螺纹、没说方向的“来一手螺纹”自己补成买开。2026-10-16 起（下单意图重构第 2 步，`docs/ORDER_INTENT_V2.md`）整句只由唯一的意图解析器读一遍：`order_intent_parse.parse`（纯函数，测试集 `tests/intent_corpus` 每句“给对或不确定、绝不给错”）读出动作（开仓 / 平几手或一半 / 全平 / 目标持仓 / 反手 / 撤单）、语气（下单、问句、建议、条件、转述、否定、整句收回）、品种（目录名，口语别名归一，可带月份“螺纹2701”）、方向（开仓：买开/开多/多 vs 卖开/开空/空；平仓：多单/空单、买的/卖出的、卖平/买平）、手数（中文数字；“两百五手”这种省略尾数不猜）、价格（“820 挂”“在 3080 买”“八百二挂”= 限价；对手价/市价 = 对价，挂单价/排队价/挂买一价 = 排队价，最新价/现价；都没说 = 规划器的统一默认）、今昨（平今/平昨/今仓/昨仓）、改口（“不对，…”取最后的说法）。`voice_front.front_order` 只挑解析器读全了的下单：开仓要有方向和手数，平仓要有手数或“一半”，全平、目标持仓、反手、撤单，或一句两单（见下）；其余——解析器说不确定、没说方向或手数、问句、建议、条件、转述、否定、带止损止盈、价差、策略——照旧交给交易 AI（追问卡）。卡由第 1 步的下单规划器出（合约、开平、今昨、价格、开仓就绪门禁都只在那里算）。只说“买/卖”（没说开、多、空）开仓时先读一次账户：同品种持着反方向的仓（“卖一手”而持有多单，可能是卖平）就交给交易 AI 问，账户读不到也交给它。没点品种的开仓、目标持仓、反手用窗口上的合约；听错的词（“互金”“对手架”）解析器不认识就整句不确定，不会落到图上的合约。
- 一句多单（2026-10-17，所有者 10-16 口径“按顺序出两张卡、各自确认”）：解析器按“然后 / 再 / 接着 / 另外”或停顿把句子拆成分句，每个分句当成一句简单话单独读（`order_intent_parse._legs`）；只有每个分句都是有把握的开仓（说了方向和手数）、平几手 / 平一半或全平，且各自点名合约（品种、月份、“这个”，全平可说“全部”）时才拆成 `legs`，每单的合约、方向、手数、价格只取自己的分句，绝不从别的分句借；任何一句拿不准或不是下单语气、价格或合约单独一段说（“…，对手价，然后…”）、夹着撤单 / 调仓 / 反手、同一单说两遍（“买一手螺纹，再买一手螺纹”）、共用一个“各买”（“螺纹2701、沪金2612各买一手”）、带条件，整句不读、请一单一单说；改了限定的“就…”重述同样不读。`legs` 交规划器：每单都是可下单的外盘品种时（解析器账户目录之外也认可下单外盘的展示名与 `instruments.FOREIGN_ALIASES` 里的明确叫法，如“美黄金”“美白银”）整句转到美元子账户，每单换成它点名的月份或主力月份（与单句外盘单同一换法），中外混在一句的留在本账户、不出卡；互不影响的一次按顺序出全部卡、各自确认；同一合约先平再动走目标持仓接力（先出第 1 张，成交后出下一张）；不限范围的全平夹别的单 `legs_entangled`；某一单只说买 / 卖而持仓是反方向、或要追问月份 / 多空时整句不出卡（`legs_unsettled`，请一单一单说）；某一单出不了卡时其余照出，并在回复里说那一单的原因。这些卡记 `intentSource=parser_legs`，语音下单免口头确认不代确认。交易 AI 的 `propose_order` 仍不接受 `legs`（#952 第三轮收窄：模型给的每一单绑不到它自己的分句上），返回 `legs_entangled` 请用户一单一单说。一句话规划出几张卡时（如今仓全平涉及几个合约）卡在界面上一次全出、各自可点，语音逐张问：先念“一共 N 张卡，一张一张确认。第 1 张：…确认吗？”，“确认/算了”只作用于这一张，再念下一张单独问（超时放弃后同样接着问，界面上已点掉的跳过）——下一张在问它的那句真正提交播放时才成为可确认的卡（念句先等豆包确认取消、等换会话，等待中不算提交，期间的“确认”碰不到它；#932 复核 10-16 16:56），那句没念出（被打断、用户先开口）就放回队首，下一声“确认 / 算了”先重念它，未念的卡口头“确认”碰不到（#932 复核）；排队的卡始终归通话本身持有，取消或超时交接途中挂断也由通话收尾一并作废（超时作废被挂断打断时，没作废完的卡留在通话上由收尾作废），新通话捞不到；被风控拦下的卡只念原因、接着问下一张可确认的，还没问到的卡对口头“确认”不可见；交易 AI 回合（委派）出的多张卡（今仓全平几个合约）同样逐张问（第 3 步）：只有第 1 张等确认，其余排队、未念不可见，语音下单免口头确认开着也不代确认；免口头确认只代确认解析器直接读出的卡（卡上 `intentSource=parser`），交易 AI 用 `propose_order` 读出的卡（`model`）一律念出、等用户说确认；会话里有两张以上没人指认的待确认卡时，单说“确认”一张也不碰（在卡上点）；说“都不要 / 全部取消”作废所有待确认卡；挂断、换对话或新业务句放弃当前卡时，排队还没问到的卡一并作废；同一合约的几条开仓腿合计核日内开仓限额。
- 出卡：定稿那一刻（或提前判停、强制判停的那一刻）Runtime 用交易 AI 的 `propose_order` 同一个下单规划器出卡（技能按动作把关：开平仓=下单出卡，全平=批量平仓，目标持仓/反手=目标持仓；合约用词由 `order_planner.resolve_words` 按目录读，打字快速路径、`propose_order` 与语音前台同一读法），取该对话账号的那套工具（原生 adapter 的 `tools_for_account`，否则与网页目标持仓路由相同的构造；只读账号拒绝），所以合约解析、今昨判定、就绪与行情新鲜度、涨跌停与最小变动、日内开仓限额、目标持仓拆段全部一致。平仓没说方向时按持仓：只持一个方向就用它，多空都有、或同品种持有两个月份就交给交易 AI 问。拒绝按工具原话（`userFacing.candidateIssues`，括号里的合约代码去掉）念；行情所在时段已收盘时说“螺纹现在不在交易时段，晚上九点开夜盘才能下单”（卡片工具收盘后报 `proposal_gate_not_ready`，决策上下文原因里是 `market_not_fresh`，也按行情所在时段换成这句，#754）。卡片念法（`card_line`）：合约、买开/卖开/买平/卖平、手数（平今/平昨）、对手价/挂单价/最新价或限价及价格，再问“确认吗？”；批量平仓逐张念（最多 4 张），有合约这次平不了（如行情不是最新）就念出来哪几个、为什么不在卡里，这种部分批量不走免口头确认，目标持仓先说“螺纹调到空 2 手，现在多 1 手”，两段的说明第 1 步共 2 步；风控没过的卡（无审批）说原因不问确认。
- 谁来念：默认（`AI_TRADER_VOICE_ACTION_SPEAK` 空或 `direct`）卡片一出 Runtime 就念（`speech_text_buffer.commit`，`actionRead inTurn=false`），豆包对这句定稿自己的回复（它的 `action` 调用或话）按迟到回复取消（`lateToolDropped` / `lateReplyMuted`）。实测（本机直连线上豆包、同一组合成语音）：说完→开口 2.43 / 2.00 / 2.25 s，而等豆包工具轮同轮替换是 3.19 / 2.75 / 2.95 s——它的 action 调用在定稿后约 0.75 s 才来、替换后约 0.9 s 才出声；定稿时就念时豆包本轮干脆没有回复。豆包有时在定稿后约 0.1 s 就调 `action`，Runtime 按迟到回复取消它；念句等这次取消结束（`response.done`，最多 2 s，`actionCancelWait`）再提交，且没有 response id 的音频帧按最后开始的那段输出归属——Runtime 自己的念句不会被当成被取消的回复丢掉（10-13 线上首轮回归“平掉一手沪金多单”的念句整段被丢、只听到 15 s 后的“没有听到确认，已放弃”，#860 修）。`AI_TRADER_VOICE_ACTION_SPEAK=turn` 保留同轮路径作对照：豆包调 `action` 时在它的工具轮里用 Runtime 这一句经 `speech_text_buffer.replacement` 同轮替换（`actionToolCall`、`actionRead inTurn=true`），先开口或去调别的工具时取消它由 Runtime 念（`actionFallback`），一言不发或 2.5 s 无动静也由 Runtime 念（`actionSilent`）。强制判停的句子 Runtime 直接念。卡片在念的那一刻才成为通话的待确认卡并进对话（用户原话、念的这句、方案卡依次发布，`origin: voice`，交易 AI 内存历史同步），之后“确认 / 算了”与原来完全相同；念之前这一轮被丢掉的（续句合并、打断、说“算了”、说了新的一句）卡片走正式放弃路由作废（`actionDropped`），不会出现在对话里，也确认不了。
- 撤单（`cancel`）：有待确认卡时“撤了 / 撤单 / 不做了 / 先不买了”放弃那张卡（`ACTION_CANCEL_WORDS`，或解析器读成撤回待确认卡）；有卡时点了品种的撤单（“螺纹那个单撤了”）不再当成放弃这张卡，交给交易 AI；没有卡时读正在挂着的委托（`GET /api/simulation/orders?active=true`，`order_is_working`），点了品种只看该品种：没有就说“现在没有挂着没成交的委托”，唯一一笔就在念的那一刻经委托栏同一条撤单路由撤一次（结果未知不重发，与挂单看护的“撤单”相同），两笔以上交给交易 AI 问撤哪笔。挂单看护里正看着的单仍走原来的 `watch_cancel`。
- 归属（#523 R1c，前台查询同样适用）：每个前台轮次在接纳时冻结它的会话、该会话绑定的交易账号和本通话的会话代次；只有会话真的换到别的账号才算动过（2026-10-19 #932 后续：会话行的 `account_revision` 是切换的写入次序，重复切到同一账号也会 +1，不再用来判动过；一轮内 A→B→A 回到原账号时与没动一样，回答属于当前账号），（hello 或窗口显示的对话变了 +1）；出卡前先读窗口当前显示的对话（与 delegate 相同），卡片在冻结的会话与账号上出。工具结果交给豆包、念出、写进对话历史、补进豆包上下文之前都复核：绑定变了、会话没了或账号被撤权、通话已挂断，这一轮就退役（时间线 `frontRetired` / `actionRetired`），不落到新的对话或账号上；退役的卡按下一条作废。
- 未念出的卡：出卡到念出之间这张卡对本通话是“没听过的”，口头“确认”与服务端待确认卡查找都跳过它；作废走卡片放弃路由并回读核实，回读不是已作废就继续保持不可口头确认。挂断时还在生成的卡同样作废。
- 不可撤回的两步（撤单、开了“语音下单免口头确认”时的确认）只在完整定稿之后、续句窗口（3 秒）过去且仍是这一轮时才执行；下单句不走提前判停。免口头确认时先确认，再把“已按你的设置直接下单”记进对话。出卡走与交易 AI 同一个技能门（order-proposal / batch-close / target-position 停用或档位不含时念统一的不可用说明）。“不要撤单 / 别撤单”这类否定句不撤。全平、撤单点名了月份（“螺纹2701”）就只动那个合约。
- 持仓方向的说法（#859，2026-10-14）：平仓句里“买的 / 买进的 / 做多的”指多单、“卖的 / 卖出的 / 做空的”指空单，“卖平 / 买平”照旧；平仓句里没被这些说法解释的“买 / 卖”（“卖一手螺纹平掉”）解析器说不确定，整句交给交易 AI（防止只有空单的账户被推断成“买平”卡）。
- 改口与取消：一句里的改口取最后的说法（手数、方向、价格、品种各自以改口为准，没改的沿用前面）；改口改了动作（平→买）、改口没有下文、改口里有听不清的数都不确定；改口指向界面（“不对，买一手这个合约 / 当前的”）就是窗口上的合约，不沿用前面说的品种（2026-10-16 起直接出卡，原来整句交给交易 AI）。订单句后 3 秒内单独说“算了”不再当续句合并，按“停”处理（`turnCancelled`，卡作废）；卡片生成中说“算了”同样；念完卡后说“算了 / 不做了”就是放弃。同一句里下单后在句末撤回（#523/#754，2026-10-14：“开三手，不对，两手沪金多单，算了。”被识别成一个 final，原先前台 cancel 后仍 delegate 出了两手卡）由解析器读成整句收回（stance retracted）、`classify` 改路由：有待确认卡 → `cancel`（作废那张卡），否则 → `retract`（以 cancel 工具执行，念“好，这单不下了。”，这一问一答按接纳时的对话绑定记进对话；卡片生成中则同“算了”停下并作废），整句不交交易 AI、不出新卡，与动作开关无关。算了在任何下单/撤单/保护词之后都算；不要了/不做了/取消只在说了买卖开平或手数之后算（“沪金的止损不要了”仍是指令）；问句、转述后面的“算了”不算；撤回词之后还有话（“算了，还是开两手沪金多单”）按后面的新单读，新单没说品种而前面说过（“开一手沪金，算了，开两手吧”）就不确定。

### 5.7 麦克风上行诊断与“没有收到麦克风声音”（2026-10-14）

起因：所有者在 Windows 网页版打电话豆包完全没听到，手机正常；服务端时间线没有任何 transcription，而 `audioPath` 原来只统计下行，分不出“网页没发音频”还是“发的是静音”。

- Runtime：`client_reader` 收到的每个麦克风帧（二进制帧或 `{"type":"audio"}`）计入 `MicStats`，挂断时写在同一行 `audioPath`（时间线与服务端日志）：`micFrames`/`micBytes`、`micFirstAt`（Runtime 读到首帧距通话开始的秒数：建会话期间客户端先发来的帧排在队里，到读取开始才计，所以偏晚；建链失败时为 0 帧）、`micMutedFrames`（客户端 `mute` 期间的帧，不进电平）、`micRmsAvg`/`micRmsPeak`（每 5 帧抽 1 帧、每 4 个样本取 1 个算 PCM16 RMS）、`silentRatio`（抽样帧里 RMS < 10 的比例）。只记数字，不记音频。判读以 `micRmsPeak` 为主：`micFrames: 0` = 客户端没发；有帧且 `micRmsPeak` 为 0 或个位数 = 全程数字静音（选错设备/系统静音）；有帧且电平正常却无 transcription = 上游识别问题。`silentRatio` 只作参考：浏览器降噪会把说话间隙压到近零，正常通话也有 0.8 左右（测试账号 2 实测 0.81，`micRmsPeak` 18283）。
- 网页：通话“听你说”且未静音时，连续 4 秒（`MIC_SILENT_MS`）麦克风块的 RMS 都低于 0.0002（约 −74 dBFS），或根本没有音频块（AudioContext 停住），状态变 `micSilent`：通话栏下多一行警示色的“没有收到麦克风声音（当前麦克风：<浏览器实际在用的设备名>）”+“到地址栏左侧的网站设置里换麦克风，蓝牙耳机选带“免提 / Hands-Free / Headset”的那一项”（同一副耳机里能枚举到带免提/Hands-Free/Headset 的输入而当前不是它时，改为直接点名“换成「…」”；桌面客户端没有地址栏，按 `CLIENT_BUILD.platform` 改写成“到系统声音设置的输入设备里…”，#875），排查步骤在旁边的“?”（根因 10-14 已确认：Windows 把一副蓝牙耳机拆成只听的“耳机/Headphones（立体声/Stereo）”和带麦的“耳麦/Headset（免提/Hands-Free）”，浏览器选了前者；`micCapture.handsFreeSuggestion` 去掉角色词后按同一设备族匹配，`enumerateDevices` 拿不到或没有同族免提项时只给通用指引），AI 球状态句为“没收到麦克风声音”；一有声音立即消失，用户主动静音、AI 在想/在说时不提示。快照 `context.voice.micSilent: true`（只在提示时出现，同时带 `micLabel` 当前设备名与可能的 `micSuggestion`）。
- 诊断导出：通话被 Runtime 结束（口头挂断、时长用完、语音通道放弃）或断线后，客户端放开这通电话（球再点就能重拨），诊断导出的 `lastVoiceTimeline` 是刚结束的这一通（#523/#875）；回复的最后几帧不足起播缓冲时，`audio_end` 一到就立即起播，不再留到下一句。通话事件里记 `microphone`（浏览器实际打开的设备：label 去掉“某某的 / 's”人名前缀、deviceId 只留前 6 位（`default`/`communications` 原样）、track settings 的采样率/声道/回声消除/降噪/自动增益、`trackMuted`、`readyState`、AudioContext 采样率与状态）与 `mic_silent`（提示出现/消失、此前收到的音频块数、AudioContext 状态）；桌面端同时写 frontend.log。

### 5.8 豆包会话不应答：念句前的取消确认与上游看门狗（2026-10-15）

起因：生产通话 315c0ee1（测试账号 1，“开三手，不对，两手沪金多单，算了。”）——Runtime 按撤回路由回答，豆包对同一句调了 `action`，Runtime 照常答它“不要回答”并 `response.cancel`，`canceled`/`done` 都到了之后 commit“好，这单不下了。”，此后 55 s 豆包没有任何事件（下行 0 帧、下一句话也没有转写），只有挂断时的 `session.close` 还被确认。本机留存的 116 通时间线里同形态共 6 次，都发生在“豆包调了工具、Runtime 丢弃并取消它的回复、随后念句”之后（这条路径 111 正常 / 5 卡死；其余 316 次念句 1 次，那次也是豆包的工具回复还在取消中就念了），#523 里没定位的“历史间歇漏播”（f1353ada / 15a6938a，“切到 15 分钟”）也是这一形态。服务器上用同版本镜像直连豆包按生产顺序复现 114 次未卡死，但 120 次里有 6 次建会话后连 `session.created` 都不回、成串出现；另一轮 200 次里有约 1 分钟所有新连接都不应答（含立即重连），之后自行恢复。结论：卡死在豆包侧、阵发性，我方事件顺序不是必要条件，因此在 Runtime 侧兜底，而不是再改取消顺序。

- 念句只有一个入口 `speak()`（delegate 逐句念、前台查询接管、下单卡、确认/取消/撤回、界面意图、复盘、提醒、超时放弃、挂断道别都经过它）：Runtime 自己发出的 `response.cancel` 未被确认（`canceled`/`done`）时先等，最多 `SPEAK_CANCEL_WAIT_SECONDS`（1 s，确认实测 0.03–0.05 s 就到；没确认也照念，时间线 `speakWait cancelAcked=false`）；在上游读取任务里调用的念句（如“已停止。”）不等。
- 上游看门狗：建会话后 `SESSION_CREATED_WAIT_SECONDS`（5 s）没有 `session.created`，或念句后 `UPSTREAM_REPLY_WAIT_SECONDS`（4 s）内这句没有开始出声（正常念句 425 次首个事件 p99 0.59 s、最大 0.98 s；只认 Runtime 念句的 `output_audio.started`（豆包自己回复的 `tts_type=default` 不算）、用户说出的字、`error`——念句后紧跟的无字 `transcription.started` 和取消确认（`canceled` 及其后的 `done`）不算，f1353ada 卡死前就紧跟过一个无字开始，`_answers_expectation`；用户的字只有超出 Runtime 已答那句的新字才算，豆包对已答句子迟到的 partial/`completed` 不算，换了数字、动作（开/平/买/卖/撤/加/减/追）、方向（多/空）或品种的 partial 算新话）。每句念句各记一条（`unheard`，#754）：豆包按提交顺序念，一个出声只答最早那句，后一句保留自己的期限，不会互相覆盖。会话还活着（念句后来过无字开始和取消确认以外的事件）却没念出来时，先在同一会话把这句连同其后还没出声的各句按顺序再念一次（`speakRetry lines=N`，每句最多一次，换会话重念时沿用；有一句已重念过就直接换会话；10-15 复测 d5902f9b：强制判停后豆包那段还没定稿时念句被吞，只回了个空的 `response.done`。#932：只重念最早那句会排到后一句后面，它的出声被当成后一句的、后一句就再也不念；现在后一句若只是慢，最多听到两遍，不会漏），仍不出声再换会话，记 `upstreamStalled waiting=session|commit`，客户端状态回“接通中”，旧会话的读取停止（它之后送来的任何东西都不播放），新开一条豆包会话（同样的说明与工具，对话最近几轮作为上下文），成功后记 `upstreamReconnected respeak=true|false`、回“听你说”并按顺序把没听到的各句再念一遍；交换期间的麦克风帧不送上游，静音/取消静音只记下、新会话就绪后再发，排队的念句一直等到交换成功或放弃（不再 15 s 后发给没就绪的会话），排在重念之后。
- 会话丢失（#754/#523）：正在用的会话发来 `session.closed`、读取任务结束或发送失败，记 `upstreamLost why=closed|ended|failed|send`，看门狗立即换会话并重念没听到的句子（以前只置 `stop`，通话活着却没有上游）；`stop` 只表示挂断时发出的 `session.close` 被确认。候选会话在 `session.created` 前关闭、或刚回 `session.created` 就关闭（同一轮读到两件事，或在回“听你说”的间隙关闭，#932）都只算这次尝试失败（`upstreamReconnectFailed error=closed`），不会把通话交给已关的会话。
- 代次：每条会话的读取任务带代次，它派生的工具处理与回合继承这个代次；会话被换掉后，旧代处理器不再往新会话发替换念句、`response.cancel` 或工具回包（`staleUpstreamDropped` / `staleToolHandler`），它的结果改为在新会话里正常念出；旧代处理器做出的下单卡没念出就作废，不会因此变成可口头确认。同一会话重复发来的工具调用（同一 `call_id`）只执行一次（`toolCallReplayDropped`）。用户打断的念句，之后不带 response id 的音频帧按“最后开始的那段输出”归属并丢弃。
- 通话结束：通话派生的回合、工具处理、读取与各看门狗都归这通电话，挂断时一并取消；它们正在等的业务调用（确认、交易 AI 的回合、出卡）不跟着取消，跑完后结果照常留在对话里，只是不再念、不再发给豆包。
- 放弃：一通电话共 `UPSTREAM_RECONNECT_ATTEMPTS`（3）条替换会话（按剩余次数算，不是每次恢复 3 条），间隔 0 / 1 / 3 s，每条的握手、发送 `session.create` 与等 `session.created` 共用 5 s（发送卡住也算这次失败，#932）；都不应答时记 `upstreamGaveUp`、客户端收到 `error`“语音通道没有响应，请稍后重拨。”并结束通话（`hangupByStall`），此时不再发 `closed`，圆圈停在这条错误上而不是回到待机——不会再出现“接通着却怎么说都没反应”。挂断道别、时长用完那句卡住时，挂断等到它在新会话里念完（或放弃）再结束。
- 测试：`tests/test_voice_upstream_watchdog.py`（315c 形态的重连重念、建会话不应答、全部不应答时报错结束、取消确认先于念句及其上限、正常通话不重连；#754 起：候选关闭后下一代成功再卡与累计预算、握手与 ready 共用截止、交换中排队念句、两句被吞按序重念、前句迟到出声不解除后句、道别卡住、旧代工具处理器、发送失败换会话与静音补发、重念发送失败、`call_id` 重放、打断后无 id 音频帧、通话结束取消回合而业务调用跑完；#932：两句被活会话吞时同会话按序重念两句、候选 created 后立即关闭算失败、`session.create` 发送卡住受截止约束）。

## 6. 急停与可观察性

AI 自动模拟交易不单独占用常驻面板。当前策略状态、执行方式、保护原因和最近执行记录显示在策略面板的“运行中”卡和对话策略卡片中，“停止”一个实例不平已有持仓；用户也可直接通过文字或语音要求暂停策略或停止自动模拟交易。急停后：

- 禁止任何新 AI 委托；
- 中断持续语音会话；
- 保留所有订单、成交、止损和审计记录；
- 逐张撤销 AI 在本会话产生且仍可撤的活动委托；结果未知时只查询原单；
- 不自动平仓，除非本人明确选择“停止并平掉持仓”。

## 7. 不在本版范围

- `TqAccount`、`TqCtp` 或任何真实期货账户；
- 交易所 Level 2、逐笔委托或排队位置；
- `TargetPosTask`、追价撤单重报或自建完整 OMS；
- 多用户云端交易；
- 跨设备无人值守运行；
- 用模型输出代替 Runtime 的确定性风控与交易所事实回读。
