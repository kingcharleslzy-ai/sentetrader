- 网页前端：发布到 `https://qilinshuzhi.com/trader/`（2026-09-30 起；旧的 `/ai-trader/app/` 与 `/ai-trader` 介绍页已停用、返回 404）。管理员后台是同一构建的独立入口 `https://qilinshuzhi.com/trader/admin`（2026-09-30 拆出、10-01 定址，交易页右上角与设置里的入口已移除）。下载页 `https://qilinshuzhi.com/trader/download` 由官网应用（qilinshuzhi-site）提供，列出已发布桌面版本的中文更新日志：每次网页构建由 `build:web` 从 CHANGELOG 的已发布版本段（跳过 Unreleased，去掉维护记录并截断到第一句、最多 90 字）生成 `/trader/changelog.json`（最近 20 个版本），官网只显示不高于更新源 `latest.json` 版本的最近 10 个。自动更新源 `/ai-trader-updates/` 与安装包 `/downloads/ai-trader/` 路径不变（已安装客户端依赖它们）。
- 云端 Runtime：部署到腾讯云上海主机（2026-09-16 起，此前为美国 VPS；迁移手册 `RUNTIME_MIGRATION.md`），仅监听 `127.0.0.1:18000`，由 `https://ai-runtime.qilinshuzhi.com:8443` 的 Nginx 反向代理对外提供 HTTPS；保留该机 sing-box/Reality 已使用的 443 端口。
- 网页使用 Runtime 的本站账号认证，支持所有者与邀请码注册的成员。验证后换取 Secure HttpOnly Cookie；密码、快期凭据、模型 API Key 和 Runtime 令牌不得写进前端制品。

用户消息中的 `qinlinshuzhi.com` 当前没有 DNS 记录；仓库更新源和实时 DNS 均指向 `qilinshuzhi.com`，因此本方案使用后者，不创建一个拼写近似的新域名。


`VITE_APP_BASE_PATH=/trader/` 同时约束 HTML 资源、PWA `start_url`、`scope`、`id` 和图标路径，避免挂到子目录后出现白屏或 Service Worker 越界。网页版（2026-10-06 起）注册 `/trader/sw.js`（scope `/trader/`，源文件 `apps/client/src/sw.js`）：只把同源 GET 导航交给网络、断网时回一张内联离线页，不缓存任何页面和资源（没有预缓存清单，`check:web` 断言），所以发布后不会出现旧外壳；它让安卓 Chrome 给出一键安装，并接收锁屏提醒（2026-10-06：`push` 显示 Runtime 发来的通知，`notificationclick` 聚焦已开窗口并把 `?open=` 去处交给它，或按去处新开）。锁屏提醒的 VAPID 私钥由 Runtime 从 `AI_TRADER_WEBPUSH_VAPID_PRIVATE_KEY_FILE`（compose secret `webpush_vapid_private_key`，PEM / P-256，属主 999:999、0400；不设即 `/dev/null`，锁屏提醒显示“服务器还没开通”）读取，公钥经 `GET /api/app/push` 给客户端；换私钥会让所有已开设备失效，需要各自重新打开。`sw.js` 与 `manifest.webmanifest` 留在站点机（不在 `assets/`，不上 OSS），由 `/trader/` location 以 `no-cache` 提供；桌面客户端仍注销一切 Worker 与缓存、从不注册。Service Worker 只是可选增强：客户端所有读取、注册、`ready` 都经 `serviceWorkerPolicy.ts` 的封装，浏览器配置档案里 Worker 存储损坏（`InvalidStateError`、`SecurityError`）时只在控制台记一条警告、失去安装/离线页/锁屏提醒，绝不阻断首屏渲染；`ready` 永不返回时锁屏提醒 8 秒超时、启动最多等 3 秒（2026-10-13）。页面头带 iPhone 主屏幕图标 `icons/apple-touch-icon.png`（180 px，不透明）与 `apple-mobile-web-app-*` 标签。候选检查还会拒绝 localhost Runtime，并回读 `liveTrading=disabled`。

### 最低客户端版本（MIN_CLIENT_VERSION）

客户端每个 Runtime 请求上报 `X-AI-Trader-Client`（平台/版本/构建 sha），Runtime 在响应头回 `X-AI-Trader-Client-Compat` 判定（ok / outdated / unknown，Runtime 只判定客户端是否过旧），`/healthz` 的 `minClientVersion` 即 `services/trader-runtime/src/trader_runtime/client_compat.py` 里的 `MIN_CLIENT_VERSION`。判定只提示（设置 → 关于 → 软件版本行旁一行），不拦截请求；网页版是否需要刷新由网页客户端自己对照页面旁的 `version.json` 判断（Runtime 与网页分开发布，Runtime 不知道网页当前部署的构建）。**何时提高 `MIN_CLIENT_VERSION`：只在契约基线（`services/trader-runtime/contracts/openapi-baseline.json`）确认必须破坏、且随版本准备 PR 一起**——平时保持不动，旧客户端靠响应头提示更新、网页版靠对照 version.json 提示刷新。

## 腾讯云 Runtime 生产部署

生产环境从 `deploy/vps/.env.production.example` 创建服务器本地 `.env.production`，其中只保存各 Secret 文件的绝对路径；Secret 目录和文件权限必须分别限制为 `0700` 与 `0600`，不得提交密码哈希、会话密钥、API Key 或交易凭据。账户密码使用交互脚本生成带随机盐的 scrypt 哈希，命令行参数和 shell history 都不会出现明文：

```bash
services/trader-runtime/.venv/bin/python services/trader-runtime/scripts/hash_owner_password.py
```

Runtime 只读取密码哈希；快期和模型凭据分别由 TqKq Sidecar 与 Runtime 从 Docker Secret 文件读取。ProxyAPI 密钥使用 `AI_TRADER_MODEL_API_KEY_FILE`，既有 DeepSeek 部署仍可沿用 `DEEPSEEK_API_KEY_FILE`。登录接口返回的 `bindings` 只包含是否已配置、模型提供方、模拟/只读状态和档案 ID。然后在仓库根目录运行：

```bash
docker compose --env-file deploy/vps/.env.production -f deploy/vps/docker-compose.yml config
docker compose --env-file deploy/vps/.env.production -f deploy/vps/docker-compose.yml up --build -d --wait
```

Runtime 生产镜像只含 Python 依赖（openai SDK 直连各供应商），生产模板显式使用 `AI_TRADER_AGENT_MODE=native`。镜像自身仍以 Fake Agent 作为缺省值，只有服务器本地生产配置与模型 Secret 同时存在时才启用真实模型。

`deploy/vps/nginx-ai-trader-runtime.conf` 只把 `/healthz` 和 `/api/` 转给 `ai_trader_runtime` upstream（内容为单独的 include 文件 `/etc/nginx/ai-trader-runtime-upstream.conf`，一行 `server 127.0.0.1:<port>;` 指向当前服务槽），并为认证和普通 API 分别限流。全局请求体上限 1m，只有 `POST /api/strategy-backtests/browser-result`（本机算完的回测报告，最多 2000 笔逐笔，可超过 1 MiB）单独放宽到 8m；改这条路由的代理设置要与 `/api/` 块同步，且与其他模板改动一样先 nginx、后 Runtime。两个 API location 的 `X-Forwarded-For` 用 `$remote_addr` **覆盖**而非 `$proxy_add_x_forwarded_for` 追加（2026-10-11，#735）：uvicorn 以 `--forwarded-allow-ips=*` 取 XFF 最左项当作 `request.client`，追加会把直连 8443 客户端伪造的最左项透传成身份，owner 登录/注册失败预算（owner 来源键 5 次、每 IP 失败键 20 次锁定）就能靠轮换 XFF 绕过——旧版游客额度不受该 XFF 链路影响：生产游客一直读的是 nginx 覆盖过的 X-Real-IP，旧游客代码直接信任该请求头属于直连/无代理场景的隔离缺陷，由同一责任入口一并修复；覆盖后 `$remote_addr` 是 realip 还原出的真实地址（直连对端，或可信官网 `112.124.42.19` 转发的真实访客），两条公网路径下 `request.client` 恒为真实访客。应用侧按访客记账只有一个责任入口 `trader_runtime.auth.visitor_ip`（取规范 `request.client`，缺 client 保持 `unknown`）：owner 登录/注册/TqKq 限流与游客 `GuestService.ip` 共用，不读任何请求头当身份。**部署合同：先 nginx、后 Runtime，顺序不可颠倒**。`deploy-release.sh` 只在首次蓝绿迁移时安装该模板（见下节），平时改了模板要手工先行：备份现有 `/etc/nginx/ai-trader-runtime.conf` → 安装规范 XFF 覆盖模板 → `nginx -t` → reload 成功——此阶段任一步失败都**不切换新版 Runtime**，按备份回滚并 reload 后止步；规范 nginx 生效后才按正式 `deploy-release.sh` 切新版 Runtime（反过来会让新游客代码在旧追加式代理后面短暂暴露于 XFF 轮换）。回退 Runtime 可以保留规范 nginx 不回退：旧游客代码读的是 nginx 覆盖过的 X-Real-IP，与覆盖 XFF 兼容。随后按既有发布回读合同核验（#733 realip 那次即按此流程手工安装）。Runtime 与 Sidecar 共享私有网络命名空间，Sidecar 仍只绑定 `127.0.0.1`（宿主端口 18000=blue 槽、18001=green 槽）；容器均保持非 root、只读根文件系统、去除 Linux capabilities，线上模拟委托走各自快期账号的 `TqKq`，Runtime 健康门禁固定回读 `liveTrading=disabled`。

### Runtime 蓝绿无缝部署

`docker-compose.yml` 定义两个 Runtime 槽：`trader-runtime-blue`（netns 8000 / 宿主 127.0.0.1:18000）与 `trader-runtime-green`（netns 8001 / 宿主 127.0.0.1:18001），同一镜像、同一数据卷、同一环境，仅监听端口与 healthcheck 不同；两个槽都带 `--timeout-graceful-shutdown 5`，保证 `docker stop` 的 10 秒窗口内能走完 lifespan——优雅退出会主动释放实例租约，另一槽在一个心跳（≤10 秒）内接管，不会出现双 leader（新槽启动时若旧槽仍持有租约，只会以 standby 身份服务 HTTP）。快讯/新闻/研究/提醒/复盘等后台生产者也只在租约持有者上跑（2026-10-12）：切换重叠期间新槽只读共享库，接手后立即补跑当天到期的任务（08:45 预生成、06:00 记忆整理、15:15 复盘），不因换槽漏掉当天，也不让两槽各调一遍模型。

`deploy-release.sh` 生成的主机脚本按以下序列发布（主机 `/etc/nginx/nginx.conf` 须有 `worker_shutdown_timeout 8s;`，缺了脚本先补上并 reload 一次：换槽 reload 后旧 worker 会继续承接浏览器的 HTTP/2 长连接和其上的事件流重连，旧槽停掉后这些窗口一直 502，2026-09-27 实测一个窗口持续约一小时；限时关闭让浏览器在旧槽停止前改连新 worker）：构建镜像 → 启动空闲槽（`up -d --no-deps --wait trader-runtime-<idle>`，不触碰 sidecar 与其 netns 内的 tqkq-sidecar-2 / tqkq-pool）→ 轮询该槽 `/healthz` 直到 commit 等于目标 SHA（60 秒超时则中止：删新槽容器、还原 env，旧槽与 nginx 不动）→ 把 upstream include 写成新槽端口，`nginx -t` 通过后 reload（任一步失败自动还原 include 并中止）→ 等 10 秒让在途请求经旧 worker 排水（长连事件流在旧槽停止时迁移，客户端 3 秒重连静默期内无感）→ `rm -sf` 旧槽 → 按服务计划重建 sidecar netns 中需要换的容器（见下段）→ 重建 paper 引擎 → 切 `current` 软链。任一步失败走 `rollback()`：恢复 env 后只从上一 release 自己的 compose/images 与恢复后的 env 选择 overlay 与镜像——upstream include 恢复部署前原状（原有内容照写、原空文件保持空、原先不存在则删除本次迁移新建的 include），旧槽按上一 release 的镜像拉起，新槽删除。sidecar 的共享 netns 已被本次切换重建时（按服务计划重建了 sidecar 或其成员、或任一迁移形态——含 needs_migration 而 previous 已是蓝绿、include 缺失的整栈重建；旧 paper 容器仍可能留在原 namespace，因此须显式移除重建，与本次是否执行到 paper 步骤无关），先移除 namespace 的全部消费者（两槽与旧 env 启用的成员，含已换新的 active 槽），再单独移除 netns owner（`tqkq-sidecar`——`docker rm -f` owner 在消费者仍引用其 namespace 时同样 rc 0、旧消费者留在原 namespace，顺序不能交给 Docker；消费者移除失败则立即止步，不动 owner），再按依赖顺序逐条 compose 调用（旧 sidecar → 启用的 side2/pool → 旧 active 槽 → paper，均 `--no-build --no-deps --force-recreate`，上一步失败即止）从上一 release 重建整个 netns；仅 paper 被切换时保留 sidecar 与订阅、只重建 paper 与旧 active；未触任何 sidecar 成员保持原轻量回滚；legacy 整栈恢复同样受成员健康核验约束。每个启用成员（sidecar/side2/pool/paper）通过容器内只读 `/healthz` 按各自真实健康语义自证（`docker compose exec` + python/urllib，同 compose healthcheck 机制；Bearer token 只在容器内读挂载 secret，不进命令行与日志）：pool 报 `{status: ok, pool: true}`，sidecar/paper 报正确 service 身份、liveTrading disabled 且 dataStatus 为 normal/stale（stale 是数据新鲜度不算不可用；connecting/unavailable/身份不符不算恢复）。所有 rm/up/配置/成员与旧槽健康检查失败都计 `ROLLBACK_FAILED`（成员未过为 `ROLLBACK_MEMBER_UNHEALTHY`），仅全部恢复且旧槽 `/healthz` 报出上一 release 完整 SHA 与版本（读上一 release `package.json`）、liveTrading disabled 后才输出 `ROLLBACK_OK`。数据库永不回滚、不删卷、不 prune。

**服务计划**（`deploy/vps/service_plan.py`，2026-10-12）：sidecar 及其 netns 成员（tqkq-sidecar-2、tqkq-pool）发布时默认不动，以保住快期会话与订阅；主机脚本在动任何容器之前逐个判定，结果连同原因打印在部署日志里，`--dry-run` 也会只读地对生产机现状算一遍并打印。判定两件事：①镜像——sidecar 源码（`services/tqkq-sidecar`，不含测试）与上一 release 不同才算新镜像；每次发布都会打新标签，标签本身不算变化。②容器定义——compose 文件、启用的 overlay、`.env.production` 插值、端口、`extra_hosts` 等任何会改变容器的配置：用 compose 自己的 `com.docker.compose.config-hash` 比较，运行中容器的标签对比本次 `docker compose config --hash`（镜像钉成该容器正在跑的镜像，`network_mode: service:tqkq-sidecar` 解析成运行中 sidecar 的容器，与 compose 计算标签时一致）。sidecar 镜像或定义变了 → 重建 sidecar，并连同 netns 里的成员与新服务槽一起重建（namespace 换了，成员必须跟着换）；只有某个成员自己的定义变了 → 只重建该成员；都没变 → 不动。Runtime 槽每次都蓝绿切换，paper 引擎每次都换成本次镜像，RSSHub 中继由 compose 自行收敛。注意 compose 的哈希不含 secret 文件的路径与内容，换 secret 文件仍需手动重建对应容器。2026-10-12 #793 给 sidecar 加 `extra_hosts` 时旧规则只看源码、漏了这次重建，即此修复的起因。

部署不再中断进行中的回放（以暂停状态接管）：旧槽 lifespan 退出只把回放「分离」——停推进循环、不向 sidecar 发 close，回放元数据持久在 `{state_root}/replays/<id>/`；新槽收到该回放的第一个请求时惰性接管，复用原回放子数据库、以暂停状态恢复（`GET /api/replays` 列表先以 loading 占位显示，属主校验与成员隔离不变；sidecar 已不存在的回放清理元数据并 404）。接管前后同一时刻只有一个槽推进回放：旧槽退出前先停并 join 推进任务，两槽并存窗口内新槽只在新请求触发后推进。用户显式退出回放仍会真正关闭 sidecar 会话并删除记录。

成员按需连接跨槽保持（2026-09-24）：tqkq-pool 按账户 id 只起一个接入子进程，换槽窗口内新旧两槽共享它。新槽对成员的请求走 `ensure` 幂等接管现有子连接（不重启）；旧槽优雅退出只拆掉自己进程内的循环/订阅/装配（`detach`），不停池里的子连接——只有空闲回收、解绑、禁用用户才 stop。若子连接仍被外部停掉（旧版本行为或池子重启）或崩溃后换了新子进程，Runtime 在下一次账户解析或空闲扫描时发现池子没有报告它装配时的那个子进程（按 `childId` 核对），即摘除旧装配并重新装配，不会持续 503。旧槽退出后留在池里、新槽尚未接管的子连接，由新进程启动时的孤儿收养纳入同一套空闲扫描：用户超过 `idle_seconds` 仍不出现就 stop，用户一到则由 `ensure` 正常接管。

首次迁移（一次性、幂等，脚本检测到单槽 `trader-runtime` 容器或 include 文件缺失时自动执行）：删除旧 `trader-runtime` 容器 → `up -d --no-build --wait --force-recreate` 整个项目（sidecar 因新增 18001 端口映射必须重建，其 netns 内所有容器随之重启——这是一次不可避免的全栈重启）→ 先写 upstream include（18000）再安装新 nginx 模板（旧模板备份为 `ai-trader-runtime.conf.before-<short>`），`nginx -t` + reload → healthz 门禁通过后删除 green 槽。此后每次发布都是无缝的。

手动切回单槽布局（紧急回滚到蓝绿之前的形态，在主机上以 root 执行；previous 换成目标 release 目录）：


生产机（4 vCPU / 3.7 GiB）原来同时跑生产容器、RSSHub 容器和每次发布的两个镜像构建；两件事都挪到家里的 NAS（Ubuntu VM，3 核 x86、与腾讯云同架构），生产机只留生产容器。两侧各新增一个可整体回滚的部件，全部文件在 `deploy/nas/` 与 `deploy/vps/docker-compose.registry.yml`：

- **NAS 侧 RSSHub**：`deploy/nas/docker-compose.rsshub.yml`（与原腾讯云服务同一镜像 digest、同一环境变量、同样内存上限），只绑 NAS 本机 `127.0.0.1:1200`。
- **NAS 侧隧道**：`deploy/nas/ai-trader-tunnel.service`，一条 `ssh -N` 同时挂两个转发——反向 `127.0.0.1:11200`（腾讯云回环 → NAS RSSHub）与本地 `127.0.0.1:15000`（NAS → 腾讯云回环 registry `127.0.0.1:5000`）。私钥只存 NAS 的 `/etc/ai-trader-tunnel/`（root 0600，腾讯云侧只放公钥）。
- **腾讯云侧改动①（隧道端点）**：无 shell 专用用户 `ai-trader-tunnel`，`authorized_keys` 里 NAS 公钥整行限制为 `restrict,port-forwarding,permitlisten="127.0.0.1:11200",permitopen="127.0.0.1:5000",command="/bin/false"`（在任务书要求的 permitlisten 之上加 `permitopen` 把本地转发也钉死到 registry 这一个目标）——除这两个端口外这个密钥什么都做不了。
- **腾讯云侧改动②（镜像 registry）**：`deploy/vps/docker-compose.registry.yml`，独立 compose 项目 `ai-trader-registry`，`registry:2.8.3` 只绑 `127.0.0.1:5000`、数据放 `/opt/ai-trader/registry/data`、内存上限 256m，不对公网开放。Docker 对回环 registry 默认按明文 HTTP 处理，两侧 daemon 都不需要改配置。
- **NAS daemon 前提（2026-10-09 已配好）**：BuildKit 解析 FROM 基础镜像不走 daemon 的 SOCKS 代理、对 auth.docker.io 直连会超时（预拉到本地也不稳定规避，坑记 `pitfalls-cross.md`），NAS `/etc/docker/daemon.json` 需配 `registry-mirrors`（现为 docker.1ms.run + docker.m.daocloud.io）；deploy 脚本里的 FROM 预拉只是早失败检查。回滚＝清空该文件重启 dockerd。
- **生产 compose 的中继**：容器直接够不到宿主回环，`docker-compose.yml` 新增 `rsshub-tunnel` 服务（host 网络的 socat，绑 `172.17.0.1:11200` → 宿主 `127.0.0.1:11200`，与 CFTC egress SOCKS 同一模式），随发布起来；`RSSHUB_URL` 缺省值改为 `http://172.17.0.1:11200`。本地 `rsshub` 服务移进 `local-rsshub` profile 作回退，默认不启动，发布脚本在没有 `AI_TRADER_LOCAL_RSSHUB=1` 时会移除旧版部署的本地副本容器。

**源码上传连接**：工作站默认经 `mac-mini-cc` SSH 跳板连接 NAS（后台 Mac 与 NAS 在家中 LAN），仅 nas-registry 模式的 NAS 源码上传、构建、digest 回读和旧源码清理共用此路径；host 与 remote-save 始终保留原直连，即使目标 alias 恰好同名也不隐式加跳板；`--nas-jump <alias>` 可明确指定跳板，在后台 Mac 本机运行则用 `--nas-jump none`。跳板失败显式停止，不自动切路径；回退原直连用 `--nas-jump none`（或 `NAS_JUMP=""`），不改 TUN、路由器、NAS 构建位置、registry 或蓝绿/备份/回滚流程。

**发布构建路径**（`deploy-release.sh` 默认）：`git archive` 同时落到 NAS 的构建目录与生产机 `releases/`；NAS 在 x86_64 主机用原生 `docker build` 构建 linux/amd64（PyPI 走 aliyun 镜像，`--nas-pypi-index` 可覆盖），按完整 40 位 sha 标签 push 到 `127.0.0.1:15000`（即生产机 registry，只传变化的层）；生产机 pull 后核对 NAS push 的 digest 与本机 pull 到的 digest 一致，两镜像全部验证通过后才写 `ai-trader-runtime:<short>` / `ai-trader-sidecar:<short>` 短名标签（验证失败不发布新短名标签），后续蓝绿序列不变；已存在的短名缓存每次复用前都要经同一验证器重新证明身份（两端 digest 仍一致、短 tag 与 full-sha ref 指向同一镜像 ID），不可信即走正式 NAS 重建→push→pull→重验（旧残留短名标签可能仍在，但不复用），digest 读取本身的 SSH 失败显式报 `IMAGE_DIGEST_READ_FAILED` 而不是按空 digest 误判（#667）。NAS 或隧道不可用时发布显式失败（提示 `--build-on-host`），绝不静默回退。NAS 构建目录只留最近 5 份源码；镜像验证通过后，发布再用本次源码里的 `scripts/maintain_update_host.py --nas --apply` 清理 NAS 侧（#668）：`127.0.0.1:15000` 两个仓库的完整 sha 标签只留本次、生产当前（切换后即回滚版本）、最近 3 个两个镜像都在的 sha（按镜像的打标签时间排序，而不是镜像 Created——全缓存重建沿用旧 Created；只推上去一个镜像的不完整 sha 不占名额）及一小时内打过标签的，容器在用某个镜像的 sha 整体保留（两个标签都留），基础镜像和其他仓库不碰，构建缓存修剪到 25 GB 以内；同 sha 复用生产机已验证镜像的重跑（REUSE）同样执行这一步清理；读不到生产当前版本就不清理，清理失败只打印 `NAS_RETENTION_FAILED`，不影响发布。实测（2026-10-09，1273dce 源码）：NAS 半热构建 runtime 211s、sidecar 174s、全缓存重建 1s，峰值 load 2.10、最低可用内存 ~2.8 GiB（3 核/4 GB VM，不影响其上 runner）；首次 push 两镜像 27s+29s（registry 落盘 ~321 MiB），源码变更后增量构建 29s + 增量 push 15s（~92 MiB 变化层），无变化重推 <1s；生产机 pull 两镜像 13s，两端 manifest digest 与镜像 ID 逐项一致。对照生产机本机 no-cache 全量构建：runtime 43s、sidecar 36s，峰值 load 1.66、最低可用内存 ~1.38 GiB（空载 1.63 GiB）——此后这类负载不再落在生产机。隧道断开实测：腾讯云 11200 连接被拒在 0.2 ms 内快速失败（远小于 15s 源级超时），NAS 侧重启隧道后自动恢复。

**切换步骤**（协调者在下一次正式发布时执行；此前生产 RSSHUB_URL 仍指本地容器）：
1. 确认 NAS `ai-trader-tunnel` active 且腾讯云 `curl -s http://127.0.0.1:11200/healthz` 通（部署本 PR 时已验证并保持运行）。
2. 腾讯云加一条 UFW 规则放行容器网段到中继：`sudo ufw allow from 172.16.0.0/12 to 172.17.0.1 port 11200 proto tcp comment 'ai-trader rsshub tunnel relay'`（容器→宿主 docker0 地址会过 INPUT 链，与 CFTC 1080 规则同理）。
3. 正常发布。新 compose 起来后 `rsshub-tunnel` 中继随发布上线，本地 rsshub 容器被移除，`RSSHUB_URL` 缺省即隧道；发布后回读 `/api/research/flash` 各源仍在（含金十/华尔街见闻等 RSSHub 源）。
4. 若 `.env.production` 里显式设过 `RSSHUB_URL`，改成 `http://172.17.0.1:11200` 或删除该行走缺省。

**回退步骤**（恢复生产机本地 RSSHub）：腾讯云 `/opt/ai-trader/.env.production` 写 `AI_TRADER_LOCAL_RSSHUB=1` 与 `RSSHUB_URL=http://rsshub:1200` 后重跑发布（或手工 `docker compose --profile local-rsshub up -d rsshub` 并重启 Runtime 槽）；删 UFW 11200 规则。NAS 侧 `docker compose -p ai-trader-rsshub down` + `systemctl disable --now ai-trader-tunnel`。镜像构建回退：发布命令加 `--build-on-host`（或 `--build-host <别名>`）；registry 容器 `docker compose -p ai-trader-registry down` 可整体移除（`/opt/ai-trader/registry/data` 保留，重启用不丢）。

**隧道断开的降级**：RSSHub 各路由独立超时（`RSSHUB_TIMEOUT_SECONDS=15`、每源 15 秒上限），连接被拒即刻失败，快讯流只是少了 RSSHub 几个来源、其余照常合并，日志记 INFO，不影响 Runtime 主链路（`research_live.py` 的源级容错，2026-10-07 起就是这个行为）。中继 socat 与隧道本身都不在蓝绿链路里，起不来不判发布失败。

### 多人接入（M1a）：接入池与按需装配

没有本站模拟盘的部署里，快期登录（M1b）让接入池 verify 口令、把密码 AES-256-GCM 密封进库、建 `tqkq-pool` 账户行并立即装配（2026-10-30 起配置了本站模拟盘的部署不再绑定，见 M1b 一节；绑定/解绑接口下线、只回 410）；连接子进程只在有人在线时存在，最后一个授权用户心跳超过 `AI_TRADER_ACCOUNT_IDLE_SECONDS`（默认 1800 秒）后由 Runtime 自动回收，下一次请求自动重装配。主账号（accounts 文件里的静态账户）永不回收，行为与单账户部署逐字节一致。

缺省部署（不带 `AI_TRADER_TQKQ_POOL=1`）不启用任何池逻辑；覆盖层由 `deploy-release.sh` 仅在 `.env.production` 含该标记时追加 `docker-compose.pool.yml`（`tqkq-pool` 服务复用 sidecar 镜像、`command` 起池、共享主 sidecar 网络命名空间、独立数据卷、read_only + tmpfs；控制面 19010，子接入进程从 19100 起按需分配）。启用步骤：

1. 生成托管主密钥：`head -c 32 /dev/urandom | base64 > /opt/ai-trader/secrets/credential-key && chmod 600 /opt/ai-trader/secrets/credential-key && chown 999:999 /opt/ai-trader/secrets/credential-key`（32 字节 base64，单行；容器以 uid 999 读 secret，属主必须与其它 secrets 一致，否则 Runtime 启动报 `credential_key_file_invalid`）。
2. `.env.production` 追加 `AI_TRADER_TQKQ_POOL=1`、`AI_TRADER_CREDENTIAL_KEY_FILE_HOST=/opt/ai-trader/secrets/credential-key`；可选 `AI_TRADER_TQKQ_POOL_MAX`（默认 8，同时在线的接入子进程上限，超出的绑定排队，接口返回 503 `runtime_capacity_full`）、`AI_TRADER_ACCOUNT_IDLE_SECONDS`（默认 1800）。
3. 按正常发布流程部署（`deploy/vps/deploy-release.sh <sha>`）；若目标 SHA 已是 current（脚本会跳过部署），在主机上把 `  tqkq-pool:\n    image: ai-trader-sidecar:<short>` 追加到该 release 的 `images.yml` 后手动执行 `docker compose -p ai-trader-production --env-file /opt/ai-trader/.env.production -f docker-compose.yml -f images.yml -f docker-compose.pool.yml up -d --no-build --wait`（2026-09-22 首次启用即如此）；标记存在时脚本自动多写 `tqkq-pool` 镜像行并追加覆盖层文件（含回滚路径），否则命令与单账户逐字节一致。
4. 回读：`/healthz` 正常；`GET /api/accounts` 仍只列默认账户；服务器上 `curl -H "Authorization: Bearer $(cat /opt/ai-trader/secrets/tqkq-sidecar-token)" http://127.0.0.1:19010/pool/accounts` 列出运行中的子进程（`GET /pool/accounts`，带 capacity）。
5. 凭据安全边界：快期密码只经登录（或后台「行情源」添加行情账号）进入，AES-256-GCM（AAD=user_id）密封存 `tqkq_credentials` 表；接入子进程的口令由池经 stdin 一次性传入，不落盘、不进命令行与环境变量；`credential_key` 丢失即无法解封（bind 报错），不会退化成明文。
6. 子进程身份（2026-10-12）：池每次起子进程都生成一枚随机 token 和 `childId`。`POST /pool/accounts/{id}/start`（含幂等接管）的答复带该子进程的 `token`，`GET /pool/accounts` 只列 `childId` 不列 token；子进程的账户/持仓/委托/状态接口只认自己的 token，池的共享 token 在子进程上只开 `/v1/public-market/*`。Runtime 用这枚 token 装配该账户，并以 `childId`+端口核对“还是同一个子进程”：子进程崩溃后端口即使被别的账户的子进程拿到，旧装配的请求也是 401（下单如实记“未发送”），请求时或空闲扫描（每 60 秒）发现 childId 变了就摘掉旧装配、在新子进程上重装；池答复不带 token 时拒绝装配（`pool_protocol_error`），不退回共享 token。刚空出的端口隔离 5 分钟再分配（只为减少抖动，不是安全边界）。本项改动池与 Runtime 的协议，二者须同批上线：`deploy-release.sh` 在 sidecar 源码变化时会连同 `tqkq-pool` 一起重建，换槽到池重建之间的几十秒里成员账户装配会失败、重建后自动恢复。

回滚＝去掉 `AI_TRADER_TQKQ_POOL=1` 重新部署：`tqkq-pool` 容器与覆盖层消失，已绑定账户的行与历史保留（`provider_kind=tqkq-pool` 的行不会被启动时的 disable 扫描标记），`AI_TRADER_TQKQ_POOL_URL` 未配置时 Runtime 按单账户行为运行；托管凭据留在库里，再次启用并放回同一密钥后可继续解封。首次启用必须与本版本部署同批进行——先加了标记再部署旧版本会因 compose 缺少覆盖层文件而失败。

### 多人接入（M1b）：快期账号直接登录

M1b 在同一覆盖层上开放登录页直登：`POST /api/auth/tqkq`（body `{username, password, inviteCode?}`）让池验证口令，首次登录校验邀请码后建 role=user 用户；没有本站模拟盘的部署里绑定并装配快期账户、之后每次登录重新密封最新口令，配置了本站模拟盘的部署里（2026-10-30 起，#1205）只落到自己的本站模拟账户，快期口令只核验身份。登录失败按 IP 与用户名双键限频（沿用 owner 登录的 15 分钟窗口）；登录页只有这一个表单（2026-09-30；2026-10-04 起客户端所有登录都走它，未知新账号名带 `canRegister`、无接入池时 404 `account_not_found`，确认后走 `POST /api/auth/owner/register`）：用户名是 Runtime owner（不分大小写）或分享码注册的账户（`cloud_users.invited_by` 不是 `tqkq-login`）时，不走池，改按本地密码校验，成功返回与 `POST /api/auth/owner` 相同的 `status: "authenticated"` 结果（带 `bindings`），失败 401 `invalid_owner_credentials`；主账号的快期用户名返回 403 `use_owner_login`，提示改用管理员账号；登录框不再链接快期注册页，底部“还没有账号？注册”切到本站注册表单（`POST /api/auth/owner/register`，邀请码必填，2026-10-05）；没有任何账户授权的 role=user 业务请求 403 `tqkq_account_required`（配置了本站模拟盘时先补开本站模拟；owner 与 local-token 模式仍回落默认账户）。快期模拟停用交易后，Runtime 每次启动幂等收尾成员的快期账户（仍是行情源的保留账户行与托管口令、只删授权，其余整套解绑），所有者的快期主账号没有下单网关；`AI_TRADER_TQKQ_POOL`、行情接力与游客行情不变。

部署侧新增两个环境变量（都带缺省，缺省行为即可用）：

- `AI_TRADER_TQKQ_LOGIN_INVITE`（默认 `1`，compose 透传）：首次快期登录是否必须邀请码。邀请码由管理员登录后创建（`POST /api/auth/owner/invite-codes`，网页 UI 与 CLI 同一接口；一次性，口令验证通过后才消费；消费与建用户同一事务，建号失败不烧码）。设为 `0` 关闭邀请码门槛（任何人的快期账号都能首次登录）。
- `AI_TRADER_STATIC_TQKQ_USERNAME_FILE`：主账号的快期用户名文件（compose 已把 `tqkq_username` secret 挂载到 trader-runtime 的 `/run/secrets/tqkq_username`，与 sidecar 同源）。同名登录返回 403 `use_owner_login`，避免主账号被误绑到普通用户；不配置则只有 Runtime owner 用户名按管理员密码校验。文件不可读时 Runtime 启动即失败（fail closed）。

回滚＝部署旧版本即可；`cloud_users` 里 `invited_by=tqkq-login` 的用户行与绑定关系保留，不影响单账户行为。

### 多人接入（M2）：用户档位

每个云端用户按档位运行（主账号不限）。档位存在数据库 `plan_tiers` 表里，由主账号在网页端随时编辑，不再经环境变量配置：首次启动自动播种三档——基础档（快期直登与无档位邀请码的默认落位：只有 deepseek-flash、每日 30 万 token、每日语音 30 分钟，不开通 AI 自主执行与联网研究）、高级档（全部已配置模型、每日 200 万 token、120 分钟语音、全功能）、测试档（全部模型、100 万 token、60 分钟语音、全功能）；播种只在空表时发生一次，主账号随后的编辑与删除不会被重启复原。每个档位可调：显示名称、默认档归属、可用模型（逐个开关，全关/全开语义为集合）、每日 token 与每日语音分钟（可不限）、七个功能开关（AI 自主执行、联网研究、行情简讯、策略管理与监控、回测、行情回放、语音通话），并可新建（从任一档复制）或删除（有人使用或为默认档时拒绝）。

档位内的限制是业务事实：模型越界 403 `model_not_in_plan`、token 超额当日 429 `daily_token_quota_exceeded`、功能未开通 403 `feature_not_in_plan`（读取类接口仍开放，`/api/ai-execution/stop`、回放退出等收尾动作永远可用；语音 socket 以 4431 拒绝）、语音分钟用完 `voice_daily_limit`（socket 4430），次日自动恢复。全局兜底 `AI_TRADER_DAILY_TOKEN_LIMIT` 仍生效，与档位取更紧者。

管理员（主账号会话）的管理面（非主账号一律 404）：`GET /api/admin/plans` 列出档位与功能/模型目录，`POST /api/admin/plans {label, copyFrom}` 新建，`PUT /api/admin/plans/{name}` 改名称/默认档/模型/额度/功能开关（部分更新：只传要改的字段，`features` 只传要改的键、未传的键保持原值；立即生效——每请求读库），`DELETE /api/admin/plans/{name}` 删除（409 `plan_in_use` / `plan_is_default`）；`GET /api/admin/users` 列出成员与用量，`PUT /api/admin/users/{username}` 改档位或停用（停用立即结束该用户会话，其后登录 401 `account_disabled`）；`POST /api/auth/owner/invite-codes` body `{"daysValid": 1–90, "plan": 档位名}`（`plan` 可省略＝默认档；带档位的邀请码让首次登录直接落在该档）；`GET /api/admin/accounts` 只读列出每个交易账户的显示名、类型、状态、执行负责人和授权名单（成员隔离核对，无写操作）；`GET /api/admin/servers?range=1h|24h|7d` 只读返回项目相关主机的资源仪表、曲线与服务状态（数据来自运维台 metrics 接口，Runtime 侧缓存 60 秒；未配置运维台令牌时返回 `{"status":"unconfigured"}`，不可达时返回缓存并带 `stale: true`）；`GET /api/admin/rum?range=1h|24h|7d` 只读返回真实用户监测汇总（见下节）。网页端同一功能在「后台管理」整页控制台（顶栏用户图标或设置 → 用户管理的“打开后台管理”进入，仅主账号可见），分概览/用户/档位/邀请码/账户与授权五个分区。

重置本站模拟账户（2026-10-30，主账号会话，只能本人操作、不进 AI 能力目录，不对成员开放，#1204）：`POST /api/admin/paper-accounts/{account_id}/reset`，body `{"confirmAccountId": 同一个 account_id}`，只收库里的 `paper:` 账户；Runtime 转给撮合引擎 `POST /accounts/{id}/reset`（同一确认字段），引擎撤活动委托、清空持仓、权益回到初始资金，成交历史保留并记一条重置命令行。编号不一致 409 `confirm_mismatch`，账户不存在 404。

后台内存诊断（2026-10-26，主账号会话，默认关闭）：`POST /api/admin/memory/trace` 打开 tracemalloc 并以此刻为起点，`GET /api/admin/memory` 读起点之后仍活着的分配（按调用栈，可带 `types=true` 看对象数量），`DELETE /api/admin/memory/trace` 关闭。只在查内存泄漏时临时打开；Runtime 重启后自动回到关闭。2026-10-26 实测交易时段的增长约 95% 不在 Python 对象里，而在 glibc 给各线程开的内存区（arena）里，所以 Runtime 容器固定 `MALLOC_ARENA_MAX=2`（`deploy/vps/docker-compose.yml`）；去掉它之前先用这个诊断复测。

迁移无需手工步骤：旧库 `cloud_users` 没有 `plan`/`disabled` 列时 Runtime 启动自动补列，已有成员保持其档位（无值按基础档）；`invite_codes` 补 `plan` 列、`plan_tiers` 表与三档播种在同一迁移里创建。回滚＝部署旧版本即可；新增表列留在库里不影响旧行为，`user_voice_usage` 表同理。

### 真实用户监测（RUM，2026-10-13）

登录后的交易页（网页、桌面、手机；游客页同样）用 Google `web-vitals` 6.2.2（Apache-2.0，打包后约 3 KB gzip）采 LCP/INP/CLS/FCP/TTFB，另记价格端到端延迟（sidecar `capturedAt` → 浏览器画出该帧，用 Runtime 下发的 `serverNow` 按最短往返校正时钟，>60 秒的旧帧丢弃）、K 线首屏出图、会话 SSE 断线时长与重连次数、页面报错按类别计数（不带报错文本）、可见时长与 JS 堆（Chromium）。页面本地按分钟累计，每 60 秒 `POST /api/telemetry/rum` 发一个汇总包（每项只有次数、总和与 21 段分段计数，典型 300–600 字节，上限 16 KB、最多 10 分钟），页面隐藏或关闭时用 `sendBeacon` 补发（bearer 登录的桌面端改用 keepalive 请求）。自动化浏览器（`navigator.webdriver`）不上报。

Runtime 侧（`trader_runtime/rum.py`）：只收登录用户或游客会话、校验 Origin、每身份每分钟 20 次尝试（认证通过后、读 body 之前就计数：坏 JSON、采集已关闭、未入样的提交同样占名额，也不会为它们新建遥测库）、白名单指标名（没有能装文本的字段），按“分钟 × 用户匿名哈希（HMAC，盐存库内）× 页面会话哈希 × 客户端 × 网络类型 × 指标”合并写入数据目录下独立的 `rum.sqlite3`（WAL，不占业务库写锁；同一页面同一分钟的多次提交合并后整行再封顶：可见时长一分钟最多 60 秒、分布类指标每个样本最多一天；进程退出时关闭该库）；接收端每小时顺手删除 14 天前的行（宿主每小时维护服务只管发布目录与镜像，碰不到 Runtime 数据卷里的库，所以清理放在写入方）。估算：每个活跃页面每分钟一次约 1 ms 的 upsert、约 5–8 行；10 个同时在线页面一天约 7–12 万行，14 天约 100 万行、约 60–100 MB。没有引入 Sentry、Grafana Faro 或 OpenTelemetry Collector：它们要多跑一个常驻服务（数百 MB 内存）和独立存储，3.7 GiB 的生产机放不下，而这里需要的只是分钟级分位数。

开关：`AI_TRADER_RUM_ENABLED=0` 整体关闭（页面收到 `enabled: false` 即停，已存数据仍可在后台看）；`AI_TRADER_RUM_SAMPLE_RATE`（0–1，默认 1）按页面会话抽样。两者均由 compose 透传（默认 1/1）。状态都以 200 回答，不用 404（浏览器会把 404 记成控制台错误）。后台页采样率低于 1 时页首常显采样率；分位数落在最后一段（60 秒以上）时只知道下限，后台标“≥ 60 秒”。页面端：断线时长在静默断流（空闲看门狗触发）时从最后一帧起算，可见时长按分钟边界分摊到各分钟，同一绘制窗口内收到多帧只量最新一帧，游客登录成员时换新的页面会话并丢弃游客身份下未发出的分钟。浸泡报告（`scripts/soak/report.py`）把每项资源的证据状态分开写（无观测 / 预热后样本不足 / 有效观察 / 疑似累积），总结论只看关键资源，没有观测、关键资源缺失或运行短于预热时不写“未见累积”。

### sidecar 镜像的内存开关（2026-10-13）

依据 `ai-trader-release-artifacts/memory-20261012/` 的调查：TqSdk 进程释放的内存 glibc 不归还，号池子进程与主 sidecar 只涨不降。sidecar 镜像装了 `libjemalloc2`（构建参数 `APT_MIRROR`，`deploy-release.sh` 在 NAS 传 `http://mirrors.aliyun.com`、生产机本机构建传 `http://mirrors.tencentyun.com`），入口 `/usr/local/bin/ai-trader-entrypoint`（源码 `services/tqkq-sidecar/docker-entrypoint.sh`）在 `AI_TRADER_JEMALLOC=1` 时设 `LD_PRELOAD=/usr/local/lib/libjemalloc.so.2`、`PYTHONMALLOC=malloc`、`MALLOC_CONF=background_thread:true,narenas:2`（不开 background_thread 不归还），子进程继承。按服务开关（`.env.production` 覆盖 compose 默认）：

| 服务 | 变量 | compose 默认 |
| --- | --- | --- |
| tqkq-pool（含全部子进程） | `AI_TRADER_POOL_JEMALLOC` | 1（灰度第一阶段，2026-10-13） |
| tqkq-sidecar / tqkq-sidecar-2 | `AI_TRADER_SIDECAR_JEMALLOC` | 1（第二阶段，2026-10-14） |
| paper-engine | `AI_TRADER_PAPER_JEMALLOC` | 1（第二阶段，2026-10-14） |

回滚：在 `/opt/ai-trader/.env.production` 把对应变量设为 0，然后部署一个与当前不同的 SHA——`deploy-release.sh` 遇到已是当前的 SHA 直接退出、不跑服务计划，所以重跑同一 SHA 不会生效；急用就部署上一版 SHA（服务定义变了，服务计划会重建该容器；改 sidecar 的开关会连带重建整个网络命名空间），否则随下一次发布生效。核对是否生效：`sudo docker exec <容器> grep -c jemalloc /proc/1/maps`（号池子进程看子进程 pid）。另两处同批改动不需要开关：每个实时 TqApi 构造后删掉自带的 2020-09 前过期非期货合约（期货行保留，`sdk_trim.py`，只认 TqSdk 3.10.2，版本或结构不符自动跳过；回测/复盘的 TqApi 不裁）；Runtime 历史 K 线缓存上限 12 条、过 TTL＋宽限（各 5 分钟）主动删除。

## 1.4 更新与存储维护

桌面更新在阿里云 OSS 与国内站点两个 HTTPS 源之间做小范围测速排序（源列表编译在 `desktop_updates.rs`）；12 秒后速率低于 64 KB/s 才换源，最后一个源必须允许跑完，按 Range 续传。下载内容在用户缓存目录暂存，暂停不破坏现有安装，重试保留已下载字节。完整包或补丁还原结果均通过现有 minisign 公钥验证后才停止本地服务并交给 Tauri 安装。

发布工具为前两个可用版本生成 BSDIFF40 补丁，用 qbsdiff 还原并核对目标哈希。清单额外签名绑定目标版本、大小、哈希、补丁哈希和基础制品；补丁接近完整包大小时不发布。缺少基础包、补丁无效或跨出支持范围时下载完整包。客户端只保留最近两个完整基包，旧客户端没有保存基包，因此进入新机制后的首次更新可能仍需全量，之后才能复用。首次安装始终提供完整包。

Windows 安装器改用逐文件 zlib 压缩，避免整体 LZMA 压缩使很小的修改也扰动整个制品。Python 打包工具固定为 6.22.2，时间戳固定，组件制品按源码/锁文件指纹复用，排除未用测试/绘图库；Rust 使用体积优化和符号裁剪。已有策略格式及模拟执行边界保留，更新操作组件和旧策略指标计算统一维护。

`scripts/maintain_update_host.py` 默认预演，`--apply` 才执行。安装于 `/opt/ai-trader/maintenance/`，现有 systemd timer 用 `OnCalendar=hourly` 按固定整点运行（保留最多 5 分钟随机延迟及 systemd 默认精度窗口），不随手动或发布后启动维护服务而顺延；`Persistent=true` 补跑停机期间错过的周期。正式部署成功后先从新版本安装该脚本与 service/timer（daemon-reload），再调用同一服务。部署失败时：远端已返回自身失败（构建失败、健康检查失败并回滚）会释放 `.deploying` 标记；连接断开或被信号中断才保留标记待人工检查，标记超过 2 小时时维护返回 `stale_deploy_marker` 并使服务失败，不再每小时静默推迟。没有 `images.yml`、超过一小时且非当前/无容器引用的发布目录视为构建失败，不占保留名额、直接回收。腾讯 Runtime 主机启用 `--docker --journal`，即使本机没有更新站点也独立清理；网站主机只清更新包与日志。更新包保留最新三个版本、当前清单及补丁基包、48 小时宽限期。Runtime 保留当前版本、最近三个发布目录、容器引用版本及其镜像；另保留所有容器（含已停止）引用的镜像、每服务最新三个不同镜像身份和一小时内的新镜像；受管仓库为两个短名仓库加 `127.0.0.1:5000` 下两个 full-sha registry 仓库（#668，前缀仓库只认完整 40 位 hex 别名），保护按镜像身份跨全部受管别名整体生效——旧镜像只有短名和 registry 别名一起解绑才真正可回收，未知仓库与非 SHA 标签不触碰，只 `docker image rm` 受管标签、不强删。daemon 别名解绑只回收生产机镜像存储；现有每小时服务另启用 `--storage`：按全部 manifest 引用图保护当前/回滚/候选及运行、停止容器使用的索引或 config 身份，每服务最新三份、一小时内发布/重推和未知根/别名及其可达子 manifest 都保留。已知旧 full-sha 根与仅由待删根引用的 OCI 子 manifest 才经官方 DELETE API 删除，再用官方 garbage-collect 回收无引用层；不使用 `--delete-untagged`，不手删仓库文件。目录缺失、分页、未知媒体类型或缺子节点均拒绝清理。检测到一小时内上传目录则暂缓；从停原 registry、启动仅独立回环端口的维护实例做 DELETE、停维护实例到 GC，全程持同一维护锁，正式 push/pull 端口停用，应用容器不重启。失败/TERM 的 finally 与 systemd ExecStopPost 通过原容器完整 ID/镜像核对恢复，只恢复本次原本运行的实例；已删除但未完成 GC 的状态原子保存供下一轮补做，成功后第二轮无候选不再停止 registry（NAS 侧 `127.0.0.1:15000` 别名与构建缓存由发布时的 `--nas` 模式回收，见上文发布构建路径）。未使用超过 24 小时的 Buildx 缓存按 2 GB 目标回收，日志限制 512 MiB；清理后空闲不足 8 GiB 返回失败。

### MT5 行情桥管理员告警（2026-10-23）

`admin_alert` 仅通过现有 Web Push Hub 投给 `OwnerAuth.username` 对应的管理员（生产 `AI_TRADER_OWNER_USERNAME=charles`，同后台能力目录的 OwnerAuth / 无用户 plan 判定）；不新增用户 id 或接收人配置、不枚举无 plan 用户。投递端再次校验身份，复用订阅、VAPID、前台设备过滤与失效订阅清理，不进入提醒中心或会话，不受普通提醒开关控制。点开 `/trader/admin?section=servers`，复用原有服务器页。该页没有独立 MT5 桥状态，未加告警时间界面。

`ForeignMarketService._fetch` 记录真实 MT5 源本轮成功/失败（空报价也失败）；备用源或 last-good 成功不能覆盖该状态。已有 `AccountReminderLoop` 每 30 秒通过同一个 Collector 刷新外盘板并判定，没人打开客户端也会运行；无 MT5 源时不运行，不另建网络探测。开市采用已有 `trading_calendar.cme_session`（Globex，含周末/日间停盘/既有节假日日历）。连续失败满 600 秒告警一次，实际成功取价恢复再发一次并写总中断分钟数；未告警计时休市清零，已告警的状态保留到真实恢复，不把收盘当恢复。超过 120 秒的源样本不证明连续故障或恢复。状态仅在内存，重启或租约接管重新计时；蓝绿只由现有 instance lease 持有者运行。启动日志：`mt5_bridge_alert_monitor_started threshold_seconds=600 producer=account_reminder_loop`。

运维维护代码可独立安装，不触发产品发布：从已合并且精确 CI 通过的提交取 `scripts/maintain_update_host.py` 和 `deploy/vps/ai-trader-maintenance.service`/`.timer`，在同一维护锁及无 `.deploying` 的窗口安装至既有位置并 daemon-reload，脚本或 service 改动先预演，再调用现有 service 两次核清理及幂等；仅 timer 改动则只安装 timer、daemon-reload 并重启 timer，回读 `TimersCalendar` 与下一触发时间，不为验证定时规则主动清理。腾讯 Runtime 与阿里云更新站点共用该 timer，须同步更新，保留各自现有 service 参数。此方式不改变 current、Runtime/Sidecar/Web 或桌面版本。发布和迁移必须从最新 main 的入口执行；入口在任何远端写入（含部署标记）或停服之前，先 fetch 刷新正式 `origin/main`，再核候选 timer 与刚刷新主线的 Git 内容一致。联网刷新失败、缺文件、读取失败或内容不同均拒绝，dry-run 同样联网检查，不回退到陈旧本地引用。只相同祖先不足以放行，隔离候选须先带入同一 timer。部署失败后的内部回滚保持原逻辑，不安装旧维护文件；手动发布旧版本须先准备带主线 timer 的候选。迁移只搬源机当前 SHA，若其 timer 过旧，须先按正式入口更新源机后再迁移。此保护随新版入口生效，不能阻止人为直接运行历史旧脚本。恢复标记未清除时先用同脚本 `--recover-registry` 回读处理，禁止手删标记绕过。GC 合同见 https://distribution.github.io/distribution/about/garbage-collection/ 。
